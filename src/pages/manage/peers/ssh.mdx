# SSH Access

openZro can run a small SSH server inside the client, reachable only over the openZro network. You don't need to
expose port 22 to the internet or manage `authorized_keys`: peers authenticate each other with the keys they already
exchange through the management service.

<Note type="warning">
    SSH access is an experimental feature. It is disabled by default and must be enabled in two places: on the
    target peer's client and in the openZro dashboard.
</Note>

## How it works

- The SSH server listens on **TCP 44338** on the peer's openZro IP. It never listens on the host's public interfaces.
- Authentication uses **peer keys**. Each client generates an SSH key pair and reports the public key to management,
  which distributes it to the other peers in the network map. A peer accepts an SSH session from another peer only if
  it has received that peer's key.
- When SSH is enabled for a peer, the client adds a firewall rule that accepts TCP 44338 from other openZro peers. The
  rule is skipped when an access policy already allows all TCP traffic to the peer.
- Access is therefore **machine-level**: any peer that an access policy connects to the target can open a session. To
  limit who can SSH into a machine, limit which peers can reach it with [access control policies](/manage/access-control/manage-network-access).

## Enabling SSH

### Step 1: Allow the SSH server on the target peer

The client refuses to start the SSH server unless it is explicitly allowed locally.

**Using the CLI:**

```bash
openzro down  # if openZro is already running
openzro up --allow-server-ssh
```

**Using the desktop app:** open the openZro tray menu, go to **Settings** and check **Allow SSH**.

### Step 2: Enable SSH for the peer in the dashboard

1. Go to **Peers** and open the target peer.
2. In the **SSH Access** card, turn on **Enable SSH server** and confirm the dialog.

You can also toggle it from the actions menu (`...`) on the peer's row in the **Peers** table.

The SSH server starts on the peer once both settings are on. Turning either one off stops it.

## Connecting

Use the `openzro ssh` command from another peer in the same network. It must run with administrator privileges,
because it reads the local peer's SSH key from the client configuration.

```bash
sudo openzro ssh 100.64.0.10
```

You can also use the peer's openZro DNS name when openZro DNS is active on your machine. The default user is
`root`; pass another one with `user@host`:

```bash
sudo openzro ssh ubuntu@my-server.openzro.selfhosted
```

| Flag | Description |
|---|---|
| `-p`, `--port` | Remote SSH port. Defaults to `44338`. |

The session is an interactive shell with a terminal. For the full list of global flags, see the
[CLI reference](/get-started/cli#ssh).

## Limitations

- **Linux, macOS and FreeBSD only** for the SSH server. A Windows peer ignores the setting and logs a warning.
- **Block Inbound Connections disables it.** A peer running with
  [Block Inbound Connections](/client/block-inbound-connections) does not start the SSH server.
- **Only the `openzro ssh` client is supported.** OpenSSH, PuTTY and other clients cannot authenticate, because the
  server only accepts peer keys distributed by management.
- **Interactive shells only.** There is no remote command execution, port forwarding, SFTP or SCP.
- **No per-user authorization.** Sessions are authorized per peer, not per openZro user, and there is no mapping of
  openZro users to local OS accounts.
- **No host key verification on the client side.** The client trusts the server it reaches over the openZro tunnel,
  which is itself authenticated with WireGuard keys.

<Note>
    Identity-based SSH (OIDC users, per-user authorization and OpenSSH support) is planned, but not available yet.
</Note>

## Disabling SSH

Turn off **Enable SSH server** in the dashboard, or restart the client without the local permission:

```bash
openzro down
openzro up --allow-server-ssh=false
```

## Troubleshooting

**`error: you must have Administrator privileges to run this command`**

Run `openzro ssh` with `sudo` on Linux and macOS, or from an elevated terminal on Windows.

**Connection refused or timeout**

- Check that the target peer runs Linux, macOS or FreeBSD and was started with `--allow-server-ssh`.
- Check that **Enable SSH server** is on for the target peer in the dashboard.
- Check that the target doesn't have Block Inbound Connections enabled.
- Check that a policy connects the two peers: `openzro status -d` should list the target as connected.

**Authentication failed**

The target has not received your peer's key yet, usually because no policy connects the two peers or the target has
not received a network map update. Verify the policy and run `openzro status -d` on both sides.
