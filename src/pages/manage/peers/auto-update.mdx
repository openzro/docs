# Client Updates

Client updates let an administrator choose which openZro version the clients in an account should run. Management
sends the target version to each client in scope, and the client tells the user an update is available or, on macOS,
installs it.

<Note>
    Client updates were added in openZro v0.53.1-alpha.75. Older clients and management servers ignore the setting.
</Note>

## Set a target version

![Client updates](/docs-static/img/how-to-guides/auto-update/dashboard.png)

Go to **Settings → Clients** and fill in the **Client updates** card, then click **Save**:

| Field | Description |
|---|---|
| **Target version** | The version clients should run, for example `0.53.1-alpha.103`. A leading `v` is removed. Leave it empty to send no update. |
| **Force silent install** | Install the update without asking the user. macOS only. |
| **Target groups** | Only peers in these groups get the update. |
| **Target peers** | Individual peers that get the update. They are not subject to the rollout ring. |
| **Exclude groups** | Peers in these groups never get the update, even if listed in Target peers. |
| **Rollout ring (%)** | Send the update to only this percentage of the peers in scope (0–100). Empty means all of them. |

With no target groups and no target peers, the whole account is in scope, still subject to the exclude groups and the
rollout ring. A peer's place in the ring is derived from its WireGuard public key, so it stays the same between syncs
and across management replicas. Raise the percentage to widen the rollout.

<Warning>
    A forced install restarts the openZro client, which briefly interrupts its connections. Exclude routing peers and
    servers with **Exclude groups** before forcing an update.
</Warning>

## How it works

1. When a client logs in or syncs, management decides whether it is in scope and, if so, sends it the target version.
2. If the client runs an older version, it fetches the update manifest of the target release from GitHub
   (`https://github.com/openzro/openzro/releases/download/v<version>/update-manifest.json`). The manifest lists each
   platform's package and its SHA-256 checksum.
3. What happens next depends on the platform:

| Platform | Behavior |
|---|---|
| **macOS** | The tray's **About** menu shows **Install update now**. The client downloads the package, checks its checksum and Apple notarization, and installs it. With **Force silent install**, it installs without asking. |
| **Windows** | The tray's **About** menu shows **Download update**, which opens the MSI download. The user runs the installer. |
| **Linux** | The tray icon shows an update badge. Update with your package manager. |

If the manifest cannot be fetched, the client retries with backoff (30 seconds up to 8 minutes). It also checks the
directive again every 30 minutes, so a raised rollout ring reaches long-running clients without a restart. A forced
install is attempted once per directive change.

<Note>
    Deployments that mirror releases can point clients at their own manifests with the
    `OPENZRO_UPDATE_MANIFEST_TEMPLATE` environment variable on the client, for example
    `https://mirror.example.com/v{version}/update-manifest.json`. `{version}` is replaced with the target version.
    Setting it to an empty value turns client updates off on that client.
</Note>

## API

The same settings are available on `PUT /api/accounts/{accountId}` under `settings`:
`client_update_target_version`, `client_update_force`, `client_update_target_groups`, `client_update_target_peers`,
`client_update_exclude_groups` and `client_update_rollout_percent`.
