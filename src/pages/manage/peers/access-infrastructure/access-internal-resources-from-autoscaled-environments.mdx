# Access Internal Resources From Autoscaled Environments

For DevOps teams managing dynamic, scalable infrastructures, maintaining secure access to internal resources as environments scale up and down is challenging. Traditional network access methods often struggle to keep pace with the rapid changes in autoscaled environments, leading to security vulnerabilities, inefficient resource utilization, and complex management overhead.

Key challenges in managing network access for autoscaled environments like Kubernetes include:

* **Dynamic Resource Management**: As pods or containers scale up and down, maintaining consistent and secure network access becomes increasingly complex.
* **Security Concerns**: Ensuring that only authorized resources have access to internal networks, especially in rapidly changing environments, is crucial but often difficult to manage.
* **Efficient Resource Utilization**: Balancing network access with resource usage, particularly in autoscaled setups, requires careful planning and execution.

This guide introduces openZro's solution for seamlessly managing network access in autoscaled Kubernetes environments by:

* **Automating Secure Access**: Demonstrating how openZro setup keys can automatically provide secure network access to dynamically created resources.
* **Enhancing Scalability**: Showcasing how openZro integrates with Kubernetes' Horizontal Pod Autoscaler (HPA) to maintain network integrity during scaling events.
* **Optimizing Resource Management**: Illustrating how openZro efficiently manages network peers as resources scale up and down, ensuring optimal resource utilization.

Let's dive into the process of using openZro to manage network access in an autoscaled Kubernetes environment.

## Prerequisites

To replicate this use case, you'll need:

* A self-hosted openZro management server (see the [self-hosting guide](/selfhosted/selfhosted-quickstart))
* [openZro](/get-started/install) installed on your local machine
* A Kubernetes cluster (local or cloud-based)
* `kubectl` installed and configured on your local machine
* [Kubernetes metrics server](https://github.com/kubernetes-sigs/metrics-server)

With these prerequisites in place, you'll be prepared to set up a secure network connection for autoscaled resources using openZro by:

1. Creating an openZro setup key for Kubernetes
2. Setting up access policies
3. Deploying a sample application with the openZro client as a sidecar
4. Configuring a Horizontal Pod Autoscaler (HPA)
5. Observing openZro's dynamic peer management

<Note>
    This guide adds each pod to the network through a sidecar, so every replica is a peer. To expose cluster
    services or the pod network through a few routing peers instead, use the
    [openZro Kubernetes operator](/manage/integrations/kubernetes).
</Note>

This process will demonstrate how openZro simplifies secure network access in autoscaled Kubernetes environments, automatically managing connections and access controls as resources scale up and down.

## 1. Creating an openZro Setup Key for Kubernetes

The first step in this process is [creating an openZro setup key](/manage/peers/register-machines-using-setup-keys) for your Kubernetes cluster. This setup key serves as a secure authentication token, allowing your cluster's pods to join your openZro network seamlessly.

To create an appropriate setup key for this use case:

1. Log in to your openZro dashboard.
2. Go to **Setup Keys** and click **Create Setup Key**.
3. Provide a descriptive name for your key.
4. Turn on **Make this key reusable** so multiple pods can use the same key.
5. Turn on **Ephemeral Peers**. This removes pods from the openZro network once they have been offline for over
   10 minutes, so scaled-down replicas don't pile up.
6. Under **Auto-assigned groups**, add a group for the pods, for example `Kubernetes Cluster`.
7. Click **Create Setup Key** and copy the generated key; you'll need it shortly.

Here's an example:

![openZro Setup Keys](/docs-static/img/manage/peers/access-infrastructure/access-internal-resources-from-autoscaled-environments/autoscaled-01.png)

This configuration allows for dynamic management of your Kubernetes pods within the openZro network. As your cluster scales up, new pods will seamlessly join the network. When pods are terminated or remain offline, they'll be automatically removed, maintaining a clean and efficient network topology.

## 2. Setting Up Access Policies

openZro's default access control policy automatically assigns all peers to the `All` group, enabling unrestricted bidirectional access between devices and users. While this default configuration allows immediate connectivity between your Kubernetes cluster and local machine, it's crucial to implement more granular access controls for enhanced security.

To create a new access policy:

1. Go to **Access Control** in your openZro dashboard and click **Add Policy**.
2. Create a policy for Kubernetes access:
   - Set the source to your local machine's group (e.g., `Local WS`)
   - Set the destination to the pods' group (e.g., `Kubernetes Cluster`)
   - Set the protocol and ports your application needs, for example TCP 8080.
3. Name the policy and click **Add policy**.

Your access policy should look similar to this:

![openZro Access Policy](/docs-static/img/manage/peers/access-infrastructure/access-internal-resources-from-autoscaled-environments/autoscaled-07.png)

Once you save your policy, it is a good practice to disable or modify the default `All` group policy to prevent unrestricted access.

![openZro Access Policies](/docs-static/img/manage/peers/access-infrastructure/access-internal-resources-from-autoscaled-environments/autoscaled-09.png)

This tailored access policy ensures that only authorized devices (your local machine) can communicate with the Kubernetes cluster, significantly improving your network's security posture. As your environment scales, this policy will automatically apply to new pods, maintaining consistent access control.

For more detailed information on configuring access policies, refer to the [openZro Access Policies documentation](/manage/access-control/manage-network-access).

## 3. Deploying a Sample Application with the openZro Client

With openZro configured, it's time to deploy your application in Kubernetes. This process involves creating a dedicated namespace, securely storing the openZro setup key, and deploying your application alongside the openZro client. Let's walk through each step:

Create a dedicated namespace to keep your openZro-related resources organized and isolated:

```bash
kubectl create namespace openzro
```

Create a Kubernetes secret for the openZro setup key:

```bash
kubectl create secret generic openzro-setup-key -n openzro --from-literal=setup-key=YOUR_SETUP_KEY
```

Remember to replace `YOUR_SETUP_KEY` with the actual setup key you created earlier. This method securely stores your key within Kubernetes.

Next, deploy your application. For this tutorial we'll use a [sample app](https://github.com/datawire/quote) that generates random quotes:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: quote
  namespace: openzro
spec:
  replicas: 1
  selector:
    matchLabels:
      app: quote
  template:
    metadata:
      labels:
        app: quote
    spec:
      containers:
        - name: quote
          image: docker.io/datawire/quote:latest
          ports:
            - name: http
              containerPort: 8080
          resources:
            requests:
              cpu: 100m
              memory: 50Mi
            limits:
              cpu: 200m
              memory: 100Mi
        - name: openzro
          image: ghcr.io/openzro/openzro:latest
          env:
            - name: OZ_MANAGEMENT_URL
              value: https://YOUR_MANAGEMENT_DOMAIN
            - name: OZ_SETUP_KEY
              valueFrom:
                secretKeyRef:
                  name: openzro-setup-key
                  key: setup-key
            - name: OZ_HOSTNAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 100m
              memory: 128Mi
          securityContext:
            capabilities:
              add:
                - NET_ADMIN
                - SYS_RESOURCE
                - SYS_ADMIN

---

apiVersion: v1
kind: Service
metadata:
  name: quote
  namespace: openzro
spec:
  ports:
    - name: http
      port: 80
      targetPort: 8080
  selector:
    app: quote
```

This deployment creates a pod running both the `quote` app and the openZro client as a sidecar. Replace
`YOUR_MANAGEMENT_DOMAIN` with your management server's domain. The client uses the setup key to connect the pod to
your openZro network, and because containers in a pod share the network namespace, the app is reachable on the pod's
openZro IP. In production, pin the image to a release tag instead of `latest`.

Deploy the app by running the following:

```bash
kubectl apply -f quote-app.yaml
```

After a few seconds, the pod appears on the **Peers** page, in the `Kubernetes Cluster` group assigned by the setup
key. From your local machine, call the app on the pod's openZro IP:

```bash
curl http://<POD_OPENZRO_IP>:8080
```

## 4. Configuring a Horizontal Pod Autoscaler (HPA)

To enable dynamic scaling of our application, we'll configure a [Horizontal Pod Autoscaler (HPA)](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale). This YAML configuration sets up an HPA that scales based on CPU utilization:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: quote-hpa
  namespace: openzro
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: quote
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 60
  minReplicas: 1
  maxReplicas: 3
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 20
```

Key points:

* We've set `minReplicas: 1` and `maxReplicas: 3` to limit scaling range.
* `averageUtilization: 20` triggers scaling at 20% CPU usage, lower than the default for quicker demonstration.
* `stabilizationWindowSeconds: 60` reduces the cool-down period for faster downscaling.

Apply this configuration with:

```bash
kubectl apply -f quote-hpa.yaml
```

Verify the resource was created by running:

```bash
kubectl get hpa -n openzro          
```

The output should be similar to:

```bash
NAME        REFERENCE          TARGETS       MINPODS   MAXPODS   REPLICAS   AGE
quote-hpa   Deployment/quote   cpu: 1%/20%   1         3         1          21m
```

These settings accelerate scaling for tutorial purposes. In production, adjust these values based on your application's specific requirements and performance characteristics.

## 5. Observing openZro's Dynamic Peer Management

Now that we've set up our application with openZro integration and configured the HPA, we can observe how openZro dynamically manages peers as the application scales. We'll use a simple load generator to trigger the autoscaling and monitor the results.

Open a new terminal window and run the following command to generate load:

```bash
kubectl run -i --tty load-generator \
    --rm \
    --image=busybox \
    --restart=Never \
    -n openzro \
    -- /bin/sh -c "while sleep 0.001; do wget -q -O- http://quote; done" > /dev/null 2>&1
```

This command creates a temporary pod that continuously sends requests to our application.

Now, in another terminal window, monitor the HPA's activity:

```bash
kubectl get hpa -n openzro -w
```

The `-w` flag enables watch mode, providing real-time updates on the HPA's status. The output should be similar to this:

```bash

quote-hpa   Deployment/quote   cpu: 2%/20%    1         3         1          23m
quote-hpa   Deployment/quote   cpu: 26%/20%   1         3         1          24m
quote-hpa   Deployment/quote   cpu: 29%/20%   1         3         2          24m
quote-hpa   Deployment/quote   cpu: 41%/20%   1         3         2          24m
quote-hpa   Deployment/quote   cpu: 63%/20%   1         3         3          25m
quote-hpa   Deployment/quote   cpu: 38%/20%   1         3         3          25m
quote-hpa   Deployment/quote   cpu: 17%/20%   1         3         3          25m
quote-hpa   Deployment/quote   cpu: 1%/20%    1         3         2          30m
quote-hpa   Deployment/quote   cpu: 1%/20%    1         3         1          31m
quote-hpa   Deployment/quote   cpu: 1%/20%    1         3         1          32m
```

If you go to the **Peers** page, you will see new peers automatically joining the network as pods scale up.

![openZro Two Peers](/docs-static/img/manage/peers/access-infrastructure/access-internal-resources-from-autoscaled-environments/autoscaled-11.png)

As you can see, all peers join the same group, meaning all share the same access policy you defined.

![openZro Three Peers](/docs-static/img/manage/peers/access-infrastructure/access-internal-resources-from-autoscaled-environments/autoscaled-12.png)

Conversely, when scaling down, the terminated pods go offline and, because the key creates ephemeral peers, are
removed from the network after 10 minutes.

![openZro Scaling Down Peers](/docs-static/img/manage/peers/access-infrastructure/access-internal-resources-from-autoscaled-environments/autoscaled-13.png)

When ready, stop the load generator by pressing `Ctrl+C` in its terminal window; eventually, you will see only one app peer in the dashboard.

![openZro Initial State](/docs-static/img/manage/peers/access-infrastructure/access-internal-resources-from-autoscaled-environments/autoscaled-14.png)

This demonstration showcases openZro's powerful capabilities in seamlessly managing network connections within a dynamic, autoscaling Kubernetes environment. openZro automatically adapts to your cluster's changing topology without any manual intervention, ensuring secure and efficient connectivity as pods scale up or down. This automation saves significant time and effort in network management and enhances your environment's security posture. By integrating openZro, you're implementing a robust, scalable networking solution that keeps pace with your application's demands while maintaining strict access controls.
