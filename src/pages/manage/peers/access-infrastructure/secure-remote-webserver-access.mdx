# Secure Remote Web Server Access: SSH Without Port Exposure

For DevOps teams, secure remote web server access is a critical challenge. Traditionally, remote SSH access has been the go-to solution since it uses the SSH (Secure Shell) protocol to create encrypted network connections, ensuring data confidentiality and integrity while authenticating users and devices.

The problem is that conventional remote SSH access introduces security and operational challenges:

* **Increased Attack Surface**: Exposing SSH ports to the internet creates potential entry points for attackers, increasing the risk of unauthorized access and security breaches.
* **Complex Network Configuration**: Configuring firewall rules and VPN setups for each server becomes unmanageable as the infrastructure scales.
* **Cumbersome User Access Management**: Lack of centralized management makes enforcing consistent access policies and maintaining audit trails difficult.

This guide introduces openZro as a secure solution for remote SSH access into a server without compromising safety by:

* **Enhancing Security**: Creating a secure overlay network that implements zero-trust principles, eliminating the need for exposed inbound ports.
* **Simplifying Network Management**: Simplifying network architecture and removing the need for complex firewall rules or VPN configurations.
* **Centralizing Access Control**: Providing a unified platform for managing user access across all servers, simplifying policy enforcement and auditing.

This approach enhances security, simplifies operations, and improves scalability - key benefits for DevOps teams managing diverse environments and requiring frequent SSH into a server.

Let's dive into the step-by-step process of setting up this secure remote access solution with openZro.

## Prerequisites

For this use case, you'll need the following prerequisites:

* A self-hosted openZro management server (see the [self-hosting guide](/selfhosted/selfhosted-quickstart))
* Single Sign-On (SSO) authentication set up with your preferred identity provider (optional but recommended for enhanced security).
* [openZro installed](/get-started/install) on your local machine.
* A virtual machine running your target web server, configured to accept incoming SSH connections.

With prerequisites in place, you'll be prepared to establish an encrypted point-to-point connection between your local machine and the remote web server by:

1. Installing openZro on the cloud VM hosting the web service
2. Configuring openZro's access control to manage permissions
3. Establishing a secure SSH connection to access the internal web service

## 1. Installing openZro on the Remote Server

Login to openZro and navigate to `Peers`. Ensure you see your local peer connected.

![openZro Local Peer](/docs-static/img/manage/peers/access-infrastructure/secure-remote-webserver-access/owyUeUn.png)

To add your remote web server to openZro's peer network, first you need to generate a setup key:

* Navigate to `Setup Keys` in the left menu
* Click `Create Setup Key`
* Configure the key by assigning it a descriptive name (e.g., "Remote Web Server"), setting an expiration date, and defining auto-assigned groups (if required). Read the documentation for [detailed setup key configuration](/manage/peers/register-machines-using-setup-keys).
* Copy the generated key to a secure location as you'll need it shortly

![openZro Creating Setup Key](/docs-static/img/manage/peers/access-infrastructure/secure-remote-webserver-access/jQ5rhEb.png)

Next, install the openZro client on the VM.

* SSH into the remote server
* Execute the following command:

```shell
# See /get-started/install for distro-specific instructions; quick one-liner for Debian/Ubuntu:
curl -fsSL https://pkg.openzro.io/openzro-archive-keyring.gpg | sudo tee /usr/share/keyrings/openzro-archive-keyring.gpg > /dev/null && echo "deb [signed-by=/usr/share/keyrings/openzro-archive-keyring.gpg] https://pkg.openzro.io/apt stable main" | sudo tee /etc/apt/sources.list.d/openzro.list > /dev/null && sudo apt-get update && sudo apt-get install -y openzro
```

The package installs and starts the openZro service. Connect it to your management server with the setup key you
generated:

```shell
openzro up --setup-key <YOUR_SETUP_KEY> --management-url https://<YOUR_MANAGEMENT_DOMAIN>
```

Check openZro status by running:

```shell
sudo openzro status
```

The expected output is similar to the following:

```shell
OS: linux/amd64
Daemon version: 0.53.1-alpha.103
CLI version: 0.53.1-alpha.103
Profile: default
Management: Connected
Signal: Connected
Relays: 2/2 Available
Nameservers: 0/0 Available
FQDN: webserver.openzro.selfhosted
Openzro IP: 100.85.105.240/16
Interface type: Kernel
Quantum resistance: false
Lazy connection: false
Networks: -
Forwarding rules: 0
Peers count: 0/0 Connected
```

Now, go back to the **Peers** page of the dashboard and ensure your remote web server is connected.

![openZro Peers Network](/docs-static/img/manage/peers/access-infrastructure/secure-remote-webserver-access/8I1WVEx.png)

## 2. Configuring openZro Access Control Policies
With both peers now connected to openZro, the next step is to configure access control rules. This step is essential to define and restrict who can access the remote server, enhancing security by limiting connections to authorized users or devices only.

* In the dashboard, go to **Access Control**
* Click **Add Policy** to open the policy editor.

openZro offers a range of options for peer access control. For comprehensive details on configuring groups and access policies, refer to the official documentation: [Managing Access with openZro: Groups and Access Policies](/manage/access-control/manage-network-access).

For this specific use case, we've implemented a simple access policy:

* **Source Group**: `Freelancers`
* **Destination Group**: `Testing Environment`
* **Protocol**: TCP
* **Port**: 22 (SSH)

Click **Add policy** to save it. The policy allows only peers in `Freelancers` to reach port 22 on peers in
`Testing Environment`.

<Note>
    New accounts have a **Default** policy that lets all peers reach each other. Disable it, or this policy will not
    restrict anything.
</Note>

![openZro Access Policy](/docs-static/img/manage/peers/access-infrastructure/secure-remote-webserver-access/AgB9Asr.png)

After establishing the policy, assign peers to their respective groups. To add the remote web server to the `Testing Environment` group:

* Go to **Peers**
* Click on the name of the peer you want to edit, in this case, `webserver`
* Find **Assigned Groups** and select `Testing Environment` from the dropdown list.

![openZro Web Server Peer](/docs-static/img/manage/peers/access-infrastructure/secure-remote-webserver-access/QXb6lLs.png)

While you're there, take note of the IP addresses listed on the left. Use the copy buttons to get the **openZro IP-Address** and **Domain Name**. Alternatively, hover over the peer's address in the **Peers** list:

![openZro IP Addresses](/docs-static/img/manage/peers/access-infrastructure/secure-remote-webserver-access/EVZssES.png)

With your remote server configured and the corresponding access policy enabled, the final step is to assign users to the appropriate group:

* Locate your local machine in the **Peers** list and click on it
* Find **Assigned Groups** and select `Freelancers` from the dropdown list.

![openZro Local User Peer](/docs-static/img/manage/peers/access-infrastructure/secure-remote-webserver-access/LoNxwd4.png)

## 3. Establishing a Secure SSH Connection to Access the Internal Web Service

openZro streamlines secure connections without traditional firewall complexities. Throughout this setup, you've implemented access controls without configuring a single firewall rule on any endpoint. This simplicity doesn't compromise security; instead, it enhances it through intuitive, group-based policies.

To verify the policy, test port 22 from a peer that is **not** in `Freelancers`. The connection should time out:

```shell
$ nc -vz -w 5 webserver.openzro.selfhosted 22
nc: connect to webserver.openzro.selfhosted port 22 (tcp) timed out: Operation now in progress
```

Then run the same test from your local machine, which is in `Freelancers`:

```shell
$ nc -vz -w 5 webserver.openzro.selfhosted 22
Connection to webserver.openzro.selfhosted (100.85.105.240) 22 port [tcp/ssh] succeeded!
```

Now you can SSH into the web server from your local machine, using its openZro domain name or IP address:

```shell
ssh user@webserver.openzro.selfhosted
```

The web server's SSH port is reachable only through openZro, and only from the peers your policy allows.
