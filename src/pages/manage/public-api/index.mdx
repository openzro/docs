# Use service users and tokens to access openZro's public API

## Service Users

Service users are non-interactive accounts that hold access tokens for the openZro API. Use them for automation
instead of a person's account: you can give them only the role they need, and automated access keeps working when
employees leave the company.

### What can you use openZro service users and access tokens for?

Most network management operations administrators do in the openZro dashboard can also be done through the API,
which the management server serves under `/api`.

The most common usage scenarios:

- **Automated scripts**: if you need to run automated scripts or infrastructure as code tools like Ansible or Terraform that configure your openZro network.
- **Third-party integrations**: if you want to integrate openZro with a third-party service, you can use a service user to provide access to your data without giving the third-party service access to your personal account.
- **Command-line tools**: if you use command-line tools like cURL to interact with your openZro network.

### Creating a service user

In the dashboard, go to **Identity → Users & Groups** and open the **Service Users** tab.

<p>
    <img src="/docs-static/img/manage/public-api/service-user-overview.png" alt="Service Users tab" className="imagewrapper-big"/>
</p>

Click **Create Service User**, enter a name and choose the role the service user should have:

| Role | API access |
|---|---|
| **Admin** | Full read and write access, except updating or deleting the account itself. |
| **Network Admin** | Read and write access to groups, policies, networks, routes and DNS. Read-only access to peers, setup keys, users, settings and the activity log. |
| **Auditor** | Read-only access. |
| **User** | No API access. |

<p>
    <img src="/docs-static/img/manage/public-api/service-user-creation.png" alt="Create Service User dialog" className="imagewrapper"/>
</p>

<Note>
    It's important to keep your service users secure, as they can provide access to sensitive data and actions within your organization. Give each service user the narrowest role that works.
</Note>

### Creating an access token

Open the user the token is for: your own user, or a service user from the **Service Users** tab. Admins can create
tokens for service users; every user can create tokens for themselves, but not for other people.

On the user's page, click **Create Access Token** in the **Access Tokens** section.

<p>
    <img src="/docs-static/img/manage/public-api/personal-access-token-overview.png" alt="Access Tokens section of a service user" className="imagewrapper-big"/>
</p>

Enter a name and an expiration between 1 and 365 days, then click **Create Token**. A token cannot be changed after it
is created.

<p>
    <img src="/docs-static/img/manage/public-api/personal-access-token-creation.png" alt="Create Access Token dialog" width="400" className="imagewrapper"/>
</p>

After the token is generated, copy it and store it in a secure place.
Once you close the dialog you cannot see the token again: openZro only stores a SHA-256 hash of it.
Tokens start with `nbp_`.

<p>
    <img src="/docs-static/img/manage/public-api/personal-access-token-example.png" alt="Created access token" width="400" className="imagewrapper"/>
</p>

<Note>
    It's important to keep your personal access tokens secure, as they can provide access to sensitive data and actions within your account. You should treat your personal access tokens like you would treat your password and never share them with anyone else.
</Note>

### Using access tokens

Send the token in the `Authorization` header with the `Token` scheme. Replace `openzro.example.com` with your
management server's address:

```bash {{ title: 'Example request with personal access token' }}
curl https://openzro.example.com/api/users \
  -H "Authorization: Token {token}"
```

The server also accepts the token with the `Bearer` scheme. Requests are authorized with the permissions of the
token's user.
