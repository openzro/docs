# Connecting from the office
A typical scenario administrators have is accessing their office networks remotely. With [Network routes](/manage/network-routes), openZro makes this easy. Still, administrators often want to avoid routing their users’ traffic via openZro when they are in the office.
To solve this, administrators can use [Posture Checks](/manage/access-control/posture-checks) and create policies that allow connection to the routing peers only if they are outside the office by using
a [Peer Network Range](/manage/access-control/posture-checks#peer-network-range) posture check with a block action.

## Example
In the following scenario, our office network is on the subnet `192.168.1.0/24`. Let's assume all users will be part of the group `route-users`, and the routing peer for our office will be inside the group `route-nodes`.
With this in mind, the goal is to create a Posture Check, create a Policy and assign a Posture Check to it, and finally create a Network Route that will expose the office subnet.

### Create a Posture Check
To create a Posture Check, go to **Posture Checks** in the openZro dashboard and click **Add Posture Check**.

Select **Peer Network Range**.

<p>
    <img src="/docs-static/img/manage/access-control/posture-checks/posture-checks-02.png" alt="Create Posture Check dialog" className="imagewrapper"/>
</p>
Select **Block** and click **Add Network Range** to enter your office subnet `192.168.1.0/24`.
<Note>
Note that if you have multiple locations that you want to see excluded, you can add multiple network ranges.
</Note>
<p>
    <img src="/docs-static/img/manage/access-control/posture-checks/posture-checks-05.png" alt="Peer Network Range check blocking 192.168.1.0/24" className="imagewrapper"/>
</p>
Click **Save**, then **Continue**, name the posture check "Exclude Office subnet" and click **Create Posture Check**.

After we conclude this step, we are ready to create a policy and assign this posture check. 
### Create a Policy
We start by creating a simple policy that will allow access from group `route-users` to group `route-nodes`.
This is needed to establish the connection between the users and the routing peer.

Go to **Access Control** in the openZro dashboard and click **Add Policy**.

On the **Policy** tab, select the group `route-users` as **Source · From** and `route-nodes` as **Destination · To**.
On the **Ports & Protocol** tab, choose `UDP` and enter port `1`.
<Note>
    The protocol and port are arbitrary: the policy only needs to connect the users to the routing peer. A common
    choice is ICMP, which also helps with troubleshooting.
</Note>
Open the **Posture Checks** tab, click **Browse Checks**, select `Exclude Office subnet` and add it.
<p>
    <img src="/docs-static/img/manage/access-control/posture-checks/posture-checks-10.png" alt="Posture Checks tab of the policy editor" className="imagewrapper-big"/>
</p>
Name the policy "Allow users to route-nodes" in **Policy name** and click **Add policy**.

We are now ready for the final step of creating the office route.

### Create a Network Route

Now, let's create a [Network Route](/manage/network-routes) that will expose the local office subnet `192.168.1.0/24`,
which will be distributed to all peers members of the group `route-users`. In this example, we will be using a routing peer named `router-01`,
which is a member of the group `route-nodes`, this way, the policy we just created goes into effect, and all peers from the group `route-users` will be able to reach
`router-01` only if they are not in the office network, due to our posture check.

Go to **Network Routes** in the openZro dashboard and click **Add Route**. Enter the network range, select the `route-nodes` group on the **Peer Group** tab, and click **Continue**:
<p>
    <img src="/docs-static/img/manage/access-control/posture-checks/connecting-from-the-office/create-route-with-posturecheck.png" alt="Create New Route with the office network range" className="imagewrapper"/>
</p>
Next, add `route-users` to **Distribution Groups**.
<p>
    <img src="/docs-static/img/manage/access-control/posture-checks/connecting-from-the-office/distribute-to-groups-posturechecks.png" alt="Distribution Groups for the route" className="imagewrapper"/>
</p>
Click **Continue**, enter "Office network access" as the **Network Identifier**, click **Continue** again, and finish with **Add Route**.
### Testing Posture Check
Now that we have created the Posture Check, the Policy, and the Network Route, we can test this configuration. In the following example, we will be testing this Posture Check from a macOS client named `client-01`, and as stated earlier, it belongs to the group `route-users`.

#### Connected from inside the office

The client is on the office Wi-Fi, in the `192.168.1.0/24` subnet. The posture check fails, so the route is not
offered to this peer:

```bash
$ openzro routes list
No networks available.
```

Traffic to `192.168.1.0/24` uses the local interface (`en0` on macOS):

<p>
    <img src="/docs-static/img/manage/access-control/posture-checks/connecting-from-the-office/netstat-routes-grep-local.png" alt="netstat showing 192.168.1.0/24 via en0" className="imagewrapper"/>
</p>

#### Connected from outside the office

The posture check passes and the route is available:

```bash
$ openzro routes list
Available Networks:

  - ID: Office network access
    Network: 192.168.1.0/24
    Status: Selected
```

<p>
    <img src="/docs-static/img/manage/access-control/posture-checks/connecting-from-the-office/netstat-routes-grep-external.png" alt="netstat showing 192.168.1.0/24 via utun100" className="imagewrapper"/>
</p>

Notice that subnet `192.168.1.0/24` is now routed through the WireGuard interface (`utun100`).

As you can see, the posture check works as expected: traffic goes through openZro only when the client is outside the
office network.
