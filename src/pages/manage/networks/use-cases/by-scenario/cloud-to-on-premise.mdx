# Cloud to On-Premise Access (VPN-to-Site)

This guide shows how to connect cloud workloads to on-premise databases and services using the Networks feature.

## What You'll Achieve

After following this guide, your cloud applications will be able to securely access on-premise databases, APIs, and services without exposing them to the public internet.

```
Cloud VM ────► openZro Tunnel ────► Routing Peer ────► Database Server
(peer)                               (on-prem)         (no openZro)
```

## Prerequisites

- An [openZro instance](/selfhosted/selfhosted-quickstart) (openZro is self-hosted only)
- Access to deploy VMs or containers in your cloud environment
- Network configuration permissions in your cloud VPC

## Step 1: Find Your On-Premise Subnet

Before configuring openZro, identify your data center network's subnet.

**On your routing peer device, run:**

```bash
# Linux
ip route | grep -E "^[0-9]"
```

Look for your local subnet, typically something like `10.100.0.0/24`.

## Step 2: Create a Network for On-Premise Resources

1. Go to **Networks** in the openZro dashboard
2. Click **Add Network**
3. Name it `On-Prem Datacenter` and click **Add Network**

## Step 3: Add Your Database as a Resource

1. In your new network, on the **Resources** tab, click **Add Resource**
2. Enter a name like `Database Servers`
3. Enter your database subnet or a specific IP (e.g., `10.100.0.0/24` or `10.100.0.50`) as the **Address**
4. Under **Destination Groups**, create a group called `on-prem-databases`
5. Click **Add Resource**

<Note>
For more granular access, add specific database IPs instead of the entire subnet. For example, add `10.100.0.50` to only allow access to your production database.
</Note>

## Step 4: Create an Access Policy

1. Click **Add Policy** on the `Database Servers` row. The destination is already `on-prem-databases`.
2. Set **Source** to `cloud-workloads` (type the name to create the group; you will add peers to it in Step 6)
3. Set **Protocol** to TCP and **Ports** to the database ports (e.g., `5432` for PostgreSQL, `3306` for MySQL)
4. Click **Continue** twice, name it `Cloud to On-Prem Databases`, and click **Add Policy**

## Step 5: Set Up the Routing Peer On-Premise

The routing peer forwards traffic from openZro to your data center network. Install openZro on a Linux server that can
reach the database:

1. In the openZro dashboard, go to **Setup Keys**
2. Create a new setup key (one-off is recommended). Add `on-prem-routers` to **Auto-assigned groups** and click
   **Create Setup Key**.

<Note>
Use a group of its own for routing peers instead of `on-prem-databases`. The `on-prem-databases` group is the policy
destination, so putting the routing peer in it would also open the database ports on the routing peer itself.
</Note>

3. On your on-premise server, run:

```bash
# See /get-started/install for distro-specific instructions; quick one-liner for Debian/Ubuntu:
curl -fsSL https://pkg.openzro.io/openzro-archive-keyring.gpg | sudo tee /usr/share/keyrings/openzro-archive-keyring.gpg > /dev/null && echo "deb [signed-by=/usr/share/keyrings/openzro-archive-keyring.gpg] https://pkg.openzro.io/apt stable main" | sudo tee /etc/apt/sources.list.d/openzro.list > /dev/null && sudo apt-get update && sudo apt-get install -y openzro
sudo openzro up --setup-key YOUR_SETUP_KEY --management-url https://<your-management-domain>
```

4. In the `On-Prem Datacenter` network, open the **Routing Peers** tab and click **Add Routing Peer**
5. Choose **Peer Group**, select `on-prem-routers`, click **Continue** and then **Add Routing Peer**

## Step 6: Deploy openZro on `cloud-workloads`

Create a setup key for your cloud workloads:

1. In the openZro dashboard, go to **Setup Keys**
2. Create a new setup key. Add "`cloud-workloads`" to **Auto-assigned groups** and click **Create Setup Key**.

**For VMs:**

```bash
# See /get-started/install for distro-specific instructions; quick one-liner for Debian/Ubuntu:
curl -fsSL https://pkg.openzro.io/openzro-archive-keyring.gpg | sudo tee /usr/share/keyrings/openzro-archive-keyring.gpg > /dev/null && echo "deb [signed-by=/usr/share/keyrings/openzro-archive-keyring.gpg] https://pkg.openzro.io/apt stable main" | sudo tee /etc/apt/sources.list.d/openzro.list > /dev/null && sudo apt-get update && sudo apt-get install -y openzro
sudo openzro up --setup-key YOUR_CLOUD_SETUP_KEY --management-url https://<your-management-domain>
```

**For containers (Docker Compose):**

```yaml
services:
  openzro:
    image: ghcr.io/openzro/openzro:latest
    network_mode: host
    cap_add:
      - NET_ADMIN
    environment:
      - OZ_SETUP_KEY=YOUR_SETUP_KEY
      - OZ_MANAGEMENT_URL=https://<your-management-domain>
    volumes:
      - openzro-config:/var/lib/openzro
    restart: unless-stopped

volumes:
  openzro-config:
```

**For Kubernetes:**

Use the [openZro Kubernetes Operator](/manage/integrations/kubernetes) for production deployments.

## Step 7: Verify Cloud Workload Group Assignment

After deploying openZro on your cloud workloads:

1. Go to **Peers** in the openZro dashboard
2. Verify your cloud workloads appear and are assigned to the "`cloud-workloads`" group
3. If using a setup key with auto-assigned groups, this happens automatically

## Step 8: Configure Your Application

Update your application's database connection to use the on-premise IP:

```python
# Example: Python with PostgreSQL
conn = psycopg2.connect(
    host="10.100.0.50",  # On-premise database IP
    dbname="production",
    user="app_user",
    password="secure_password"
)
```

Your cloud application can now securely access the on-premise database.

## Cloud-Specific Considerations

### AWS

- Use VPC endpoints where possible for AWS services
- Security groups must allow traffic from the openZro routing peer
- Consider using an Auto Scaling group for the routing peer with a static ENI

### GCP

- Firewall rules must allow traffic from the routing peer's internal IP
- Use instance groups for high availability
- Enable IP forwarding on the routing peer instance

### Azure

- Network security groups must allow traffic from the routing peer
- Consider using a Virtual Machine Scale Set for HA
- Enable IP forwarding on the routing peer NIC

## Best Practices

### Security

- Use dedicated setup keys per environment (e.g., `dev-workloads`, `staging-workloads`, `prod-workloads`)
- Restrict access policies to specific ports and protocols
- Enable [activity logging](/manage/activity) for compliance

### High Availability

- Deploy multiple routing peers and configure failover
- Monitor routing peer health with your existing tools (`openzro status` on the routing peer, or the peer's status on the **Peers** page)
- Use cloud-native load balancing where appropriate

### Performance

- Place routing peers close to the resources they serve
- Use direct peering where possible (openZro will automatically optimize paths)
- Monitor latency and throughput between environments

## Troubleshooting

**Cloud workload can't reach on-premise:**
1. Verify the routing peer is online: `openzro status`
2. Check the routing peer can reach the target: `ping 10.100.0.50`
3. Verify access policies are configured correctly

**High latency:**
1. Check routing peer placement and network connectivity
2. Verify traffic is using direct peer-to-peer connections (not relays)
3. Review cloud network configuration for bottlenecks
