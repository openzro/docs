# Remote Worker Access (VPN-to-Site)

This guide shows how to enable remote workers to securely access office resources using the Networks feature.

## What You'll Achieve

After following this guide, employees will be able to access office servers, applications, and services while working remotely—without exposing those resources to the internet.

```
Remote Laptop ──────► openZro Tunnel ──────► Routing Peer ──────► Office Server
   (peer)                                    (at office)          (no openZro)
```

## Prerequisites

- An [openZro instance](/selfhosted/selfhosted-quickstart) (openZro is self-hosted only)
- Admin access to office network infrastructure
- A server or VM at the office to serve as the routing peer

## Step 1: Connect a Remote Worker Device to openZro

If you haven't already, [install openZro](/get-started/install) on a remote worker's laptop and connect:

1. Run the application and click **Connect** in the system tray, or run
   `openzro up --management-url https://<your-management-domain>`
2. Sign in with the worker's account in the browser
3. Verify the device appears under **Peers** in your openZro dashboard

## Step 2: Add the Remote Worker to a User Group

1. In **Peers**, open the remote worker's device
2. Under **Assigned Groups**, add a new group: `remote-workers`

<p>
    <img src="/docs-static/img/manage/access-control/associate-peer-groups.png" alt="Assigned Groups on the peer page" className="imagewrapper-big"/>
</p>

<Note>
To put every device a user adds into `remote-workers` automatically, add the group to the user's **Auto-assigned
groups** under **Users & Groups**.
</Note>

## Step 3: Find Your Office Subnet

Before configuring openZro, identify your office network's subnet.

**On your routing peer device, run:**

```bash
ip route | grep -E "^[0-9]"
```

Look for your local subnet, typically something like `10.0.0.0/24` or `192.168.1.0/24`.

## Step 4: Create a Network for Office Resources

1. Go to **Networks** in the openZro dashboard
2. Click **Add Network**
3. Name it `Office LAN` and click **Add Network**

## Step 5: Add Your Office Subnet as a Resource

1. In your new network, on the **Resources** tab, click **Add Resource**
2. Enter a name like `Office Subnet`
3. Enter your office subnet (e.g., `10.0.0.0/24`) as the **Address**
4. Under **Destination Groups**, create a group called `office-lan`
5. Click **Add Resource**

<Note>
For more granular access, add specific server IPs instead of the entire subnet. For example, add `10.0.0.50` to only allow access to a specific file server.
</Note>

## Step 6: Create an Access Policy

1. Click **Add Policy** on the `Office Subnet` row. The destination is already `office-lan`.
2. Set **Source** to `remote-workers`
3. Set **Protocol** based on needs (TCP with specific ports for most apps, `ALL` for full access)
4. Click **Continue** twice, name it `Remote Worker Office Access`, and click **Add Policy**

## Step 7: Set Up the Routing Peer

The routing peer forwards traffic from openZro to your office network. Use an always-on Linux server or VM at your
office.

**Install openZro on your routing peer:**

1. In the openZro dashboard, go to **Setup Keys**
2. Create a new setup key (one-off is recommended). Add `office-routers` to **Auto-assigned groups** and click
   **Create Setup Key**.

<Note>
Use a group of its own for routing peers instead of `office-lan`. The `office-lan` group is the policy destination, so
putting the routing peer in it would also give `remote-workers` access to the routing peer itself.
</Note>

3. On your routing peer, run:

```bash
# See /get-started/install for distro-specific instructions; quick one-liner for Debian/Ubuntu:
curl -fsSL https://pkg.openzro.io/openzro-archive-keyring.gpg | sudo tee /usr/share/keyrings/openzro-archive-keyring.gpg > /dev/null && echo "deb [signed-by=/usr/share/keyrings/openzro-archive-keyring.gpg] https://pkg.openzro.io/apt stable main" | sudo tee /etc/apt/sources.list.d/openzro.list > /dev/null && sudo apt-get update && sudo apt-get install -y openzro
sudo openzro up --setup-key YOUR_SETUP_KEY --management-url https://<your-management-domain>
```

4. In the `Office LAN` network, open the **Routing Peers** tab and click **Add Routing Peer**
5. Choose **Peer Group**, select `office-routers`, click **Continue** and then **Add Routing Peer**

The office network is now set up:

    <img src="/docs-static/img/manage/networks/use-cases/by-scenario/remote-worker-access/office-lan-network.png" alt="Office LAN network with the office subnet resource" className="imagewrapper-big"/>
</p>

## Step 8: Test the Connection

From the remote worker's laptop (connected outside the office network):

```bash
ping 10.0.0.1  # Your office router
ping 10.0.0.50 # Your file server or other device
```

Remote workers can now access office resources from any location.

## Step 9: Onboard Additional `remote-workers`

For additional remote workers:

1. Have employees [install openZro](/get-started/install) and connect to your management server
2. After they connect, go to **Peers** and select their device
3. Under **Assigned Groups**, add them to the "`remote-workers`" group

Alternatively, create a setup key with "`remote-workers`" as an auto-assigned group for streamlined onboarding.

## Best Practices for Business Deployments

### Access Control

- Create specific groups for different access levels (e.g., `it-admins`, `sales`, `engineering`)
- Use protocol restrictions (e.g., only allow RDP to certain servers)
- Implement time-limited setup keys for contractor access

### High Availability

For critical connections, consider:
- Multiple routing peers at each location
- Monitoring routing peer health with your existing tools (`openzro status` on the routing peer)
- Automatic failover configuration

### Security

- Enable [Posture Checks](/manage/access-control/posture-checks) to verify device compliance
- Use [Activity Logging](/manage/activity) to audit access
- Implement MFA through your identity provider

## Troubleshooting

**Remote workers can't access office resources:**
1. Verify the routing peer is online and connected
2. Check access policies include the user's group
3. Ensure the routing peer can reach office resources locally

**Slow performance:**
1. Check routing peer placement—it should have good network connectivity
2. Consider enabling [lazy connections](/manage/peers/lazy-connection) for large deployments
3. If several routing peers serve the network, check their **Metric** values: the lowest metric is preferred
