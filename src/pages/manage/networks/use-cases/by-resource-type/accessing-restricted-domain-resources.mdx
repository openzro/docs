# Accessing restricted domain resources

This guide shows how to access restricted websites or services using openZro [Networks](/manage/networks) with [domain resources](/manage/networks#resources). Domain resources are useful when the target service is behind a load balancer with frequently changing IP addresses.

## Example scenario

A company hosts an accounting application at `accounting.example.com` on AWS infrastructure in the EU Central region. The application runs on an EC2 instance behind a load balancer.

The company wants to implement zero-trust access with role-based permissions:
- **Finance team**: HTTP/HTTPS access to `accounting.example.com` (ports 80 and 443)
- **Support team**: SSH access to the backend at `example.com` (port 22)

### Prerequisites

Before starting, ensure you have:
- [openZro clients](/get-started) installed on finance and support team devices
- [Routing peers](/manage/networks#routing-peers) configured in the AWS VPC using [setup keys](/manage/peers/access-infrastructure/setup-keys-add-servers-to-network)

## Create a network

1. Go to **Networks** and click **Add Network**.
2. Enter a name (e.g., `AWS EU Network`) and an optional description.
3. Click **Add Network**.

### Add routing peers

Open the network, go to the **Routing Peers** tab and click **Add Routing Peer**:

- Select **Routing Peers** to add a single peer (e.g., `aws-router`), or **Peer Group** to add a group of peers for
  high availability.
- Click **Continue**. On **Advanced Settings**, keep **Masquerade** on so the private network needs no extra routes,
  and use **Metric** to prioritize routing peers (lower values = higher priority).
- Click **Add Routing Peer**.

### Add the accounting subdomain resource

On the **Resources** tab, click **Add Resource** and configure:

- **Name**: `Accounting restricted subdomain`
- **Address**: `accounting.example.com`
- **Destination Groups**: create or select `accounting-subdomain`

Click **Add Resource**.

### Create an access policy for the finance team

Click **Add Policy** on the new resource's row. The destination is already set to `accounting-subdomain`. Configure:

- **Protocol**: `TCP`
- **Source**: `finance`
- **Ports**: `80` and `443`

Click **Continue** to optionally add posture checks, then **Continue** again. Name the policy (e.g.,
`Accounting subdomain policy`) and click **Add Policy**.

### Add the top-level domain resource for support

The support team needs SSH access to the backend at `example.com`. Click **Add Resource** again:

- **Name**: `Restricted Website TLD`
- **Address**: `example.com`
- **Destination Groups**: create or select `webserver`

Click **Add Resource**.

### Create an access policy for the support team

Click **Add Policy** on the `Restricted Website TLD` row and configure:

- **Protocol**: `TCP`
- **Source**: `support`
- **Ports**: `22`

Name it `Restricted Website TLD policy` and click **Add Policy**.

## Verify the configuration

The completed network shows both resources with their access policies:

![AWS EU Network with two domain resources](/docs-static/img/manage/networks/use-cases/by-resource-type/accessing-restricted-domain-resources/13-restricted-domain.png)

Use the openZro CLI to verify access. From a finance team workstation:

```bash
$ openzro networks list
Available Networks:

  - ID: Accounting restricted subdomain
    Domains: accounting.example.com
    Status: Selected
    Resolved IPs: -
```

From a support team workstation:

```bash
$ openzro networks list
Available Networks:

  - ID: Restricted Website TLD
    Domains: example.com
    Status: Selected
    Resolved IPs:
      [example.com]: 93.184.215.14, 2606:2800:21f:cb07:6820:80da:af6b:8b2c
```

Each team sees only the resources they have access to, with appropriate port restrictions enforced by the access policies.
