# Networks

openZro creates a secure peer-to-peer mesh network where devices running the openZro agent connect directly with end-to-end encryption. This enables precise network segmentation and secure remote access without exposing resources to the internet.

However, installing the agent on every machine is not always feasible. Networks solve this by letting you route traffic to entire LANs, office networks, or cloud VPCs without requiring the openZro agent on each device.

    <img src="/docs-static/img/manage/network-routes/concepts/openzro-network-routes.png" alt="openZro peers reaching a private network through a routing peer" className="imagewrapper-big"/>
</p>

## Networks vs. Network Routes

Networks is the newer, simpler way to reach internal resources, and the recommended choice for new setups. Network Routes still cover a few scenarios Networks does not, such as site-to-site routing; use whichever fits your use case.

For a detailed comparison, see our [site-to-site documentation](/use-cases/site-to-site).

## Concepts

### Networks

A Network is a configuration container that maps your on-premise or cloud infrastructure into a logical set of resources and routing peers. You can create multiple networks to represent different environments such as office networks, cloud VPCs, or data center LANs.

Go to **Networks** and click **Add Network**, then give it a name and an optional description. The dashboard then offers to add a resource, a policy and a routing peer to it.

<p>
    <img src="/docs-static/img/manage/networks/index/new-network-2.png" alt="Add Network dialog" className="imagewrapper"/>
</p>

Each network shows its resources, policies and routing peers in the **Networks** list. Click a network to manage it: its page has a **Resources** tab and a **Routing Peers** tab.

</p>

### Routing Peers

Routing peers are machines that bridge your openZro peers to your internal networks. They forward traffic from openZro clients to resources that do not have the openZro agent installed.

To add one, open the network's **Routing Peers** tab and click **Add Routing Peer**. Choose individual peers or a **Peer Group**; add several routing peers for high availability. Each client uses one routing peer at a time and fails over to another if it goes away.

<p>
    <img src="/docs-static/img/manage/networks/index/add-routing-peer-1.png" alt="Add Routing Peer dialog with a peer group" className="imagewrapper"/>
</p>

On the **Advanced Settings** tab you can disable the routing peer, turn **Masquerade** off (Linux routing peers only; other platforms always masquerade), and set its **Metric**: a lower metric means higher priority.

<p>
    <img src="/docs-static/img/manage/networks/index/add-routing-peer-2.png" alt="Routing peer advanced settings" className="imagewrapper"/>
</p>

<p>
    <img src="/docs-static/img/manage/networks/index/routing-peers-1.png" alt="Routing Peers tab of a network" className="imagewrapper-big"/>
</p>

<Note>
A network resource policy grants access to the network **behind** the routing peer, not to the routing peer machine itself. If you need to access services running on the routing peer (for example, Pi-hole, Home Assistant, or a monitoring dashboard), add the routing peer to a group and create a peer-to-peer [access control policy](/manage/access-control) with that group as the destination.
</Note>

### Resources

Resources are the machines, services, or subnets you want to access within your internal network. You can define resources as:

- Single IP addresses
- Subnets in CIDR notation (e.g., `10.0.0.0/24`)
- Domain names (e.g., `example.com`)
- Wildcard domains (e.g., `*.company.internal`), which need [DNS wildcard routing](#enable-dns-wildcard-routing) (on by default)

</p>

### Domain Resources

In addition to IP-based resources, openZro supports routing domain names. In the Dashboard, you can enter a domain name (e.g., `example.com`) or wildcard domain (e.g., `*.example.com`) instead of an IP range. openZro clients will then resolve and route traffic to that domain.


#### How Domain Resolution Works

1. When openZro connects, it configures the operating system to use openZro for resolving the specified domains. No routing rules are set up yet.
2. When an application requests a domain (e.g., `example.com`):
   - The OS sends the DNS query to openZro's Local DNS Forwarder, which runs on:
     - **macOS and Windows**: The highest available IP in your openZro range (typically `100.xxx.255.254:53`)
     - **Other systems**: Your local openZro client IP (e.g., `100.xxx.123.45:53`)
   - The Local DNS Forwarder sends the query to the Remote DNS Resolver on the routing peer, on port `5353`.
   - The routing peer resolves the domain using its local DNS configuration and returns the result.
   - The Local DNS Forwarder creates routing rules for the returned IP addresses before sending them to the application.
3. The application receives the response normally, with a slight delay on the first request.
4. Subsequent requests are served instantly from the Local DNS Forwarder's cache.

<Note>
  openZro attempts to automatically open the DNS forwarder port on routing peer firewalls, but this may fail on some systems. If you experience issues, manually open UDP and TCP port `5353` on the routing peer.

  To verify firewall access, run this command from the client device:
  `nslookup -port=5353 <routed-domain> <routing-peer-ip>` (e.g., `nslookup -port=5353 example.com 100.123.45.67`).

  Firewall blocking DNS requests is the most common cause of domain resource issues.
</Note>

<Note>
  When a routing peer cannot resolve a domain resource (e.g., an internal domain like `fileserver.corp.local`), you may need to configure a [Nameserver](/manage/dns/internal-dns-servers#configuring-nameservers-for-internal-domains) for your internal DNS and add the routing peer's group as a distribution group. See [Internal DNS Servers](/manage/dns/internal-dns-servers#domain-resources-and-routing-peer-dns) for details.
</Note>

## Manage Access to Resources

Every resource belongs to one or more groups, and access is granted with [access control policies](/manage/access-control/manage-network-access#creating-policies) that use those groups as destination. A peer can only see a resource when a policy grants access from one of the peer's groups (source) to one of the resource's groups (destination).

To add a resource, open the network, go to the **Resources** tab and click **Add Resource**. The dialog asks for:

- **Name** and an optional **Description**;
- **Address**: an IP address, a CIDR subnet, a domain or a wildcard domain;
- **Destination Groups** (required): the groups policies will target, for example `Databases` or `Web Servers`;
- **Enable Resource**: turn the resource on or off without deleting it.

Then click **Add Policy** on the resource's row to create a policy for it.

<p>
    <img src="/docs-static/img/manage/networks/index/resources-2.png" alt="Add Resource dialog" className="imagewrapper"/>
</p>

Access control policies define which peers can access which resources based on source groups, destination groups, and allowed traffic types (ALL, TCP, UDP, ICMP). When creating a policy:

- Place the resource's group in the **destination** field
- Place the peer's group in the **source** field
- Peers in the source groups will receive the resource routes and corresponding firewall rules
- Policies to resources are always one-way: resources behind a routing peer cannot open connections back to peers

<Note>
  Unlike peers, resources are not automatically members of the built-in `All` group. To use `All` group rules with resources, you must explicitly add them to this group.
</Note>

<Note>
  When you add a resource from the **Networks** list, the dashboard offers to create a policy for it right away. A resource without a policy is not reachable by any peer.
</Note>

<Note>
  **Migrating from Network Routes?** The two systems handle ACL defaults differently and the gotcha is easy to miss:

  - Legacy **Network Routes** with an empty `Access Control Groups` field receive an implicit `0.0.0.0/0 → route ALLOW ALL` permit at the firewall layer. A route with no policy attached just works.
  - **Networks/Resources** are strictly policy-driven. A resource without an attached policy is unreachable, even if the routing peer has IP connectivity to it.

  This is intentional — it aligns the new feature with the zero-trust default — but it surprises operators who replicate a working Network Routes setup as a Network and find the resource silently dropped at the firewall. Always attach at least one policy per resource (source = peer group, destination = the resource's group, scope = the protocols/ports the resource serves).
</Note>

For example, clicking **Add Policy** on the `CRM` row opens a policy dialog with the resource's group already set as destination. Here the `berlin-office` group gets HTTPS access to the CRM; click **Continue** to name the policy and save it with **Add Policy**:

<p>
    <img src="/docs-static/img/manage/networks/index/resource-acl-1.png" alt="Policy created from a resource row" className="imagewrapper"/>
</p>

<Note>
    Policies for domain or wildcard domain resources may unintentionally affect peers with IP range resources, since IP ranges can match any address. We recommend using dedicated networks and routing peers for domain-based resources to prevent unwanted access.
</Note>

## Manage Access to Routing Peer

A network resource policy grants access to the network **behind** the routing peer — traffic that is forwarded through the peer to reach backend resources. However, firewall rules for routed traffic are processed in the **forward chain**, not the **input chain**. This follows the same pattern as Linux Netfilter (iptables/nftables), where packets destined for the host itself traverse the input chain, while packets being routed to another destination traverse the forward chain. This means that a network resource policy alone does **not** grant access to services running directly on the routing peer itself.

If you need to reach services hosted on the routing peer machine (for example, Pi-hole, Home Assistant, a monitoring dashboard, or any locally bound service), you must create a separate [access control policy](/manage/access-control) with:

- **Source**: the group containing the peers and users that need access
- **Destination**: a group that includes the routing peer

This additional policy ensures that the routing peer's input chain allows inbound connections from your openZro peers. Without it, traffic destined for the routing peer's own IP will be dropped even if there is a valid network resource policy for the subnet behind it.

<Note>
    This is a common pitfall when the routing peer also runs local services. Remember: network resource policies control forwarded traffic (forward chain), while peer-to-peer access control policies control traffic to the peer itself (input chain). You need both if you want to access the routing peer **and** the resources behind it.
</Note>

## Enable DNS Wildcard Routing

Wildcard domain resources need DNS wildcard routing, which is enabled by default for new accounts. With it, the routing peer resolves domains instead of the client.

This is also useful for regular domain resources when you want to:

- Resolve domain names using the routing peer's DNS infrastructure
- Route traffic through a geographically nearby routing peer

The setting is under **Settings** > **Networks** > **Enable DNS wildcard routing**:

<p>
    <img src="/docs-static/img/manage/networks/index/settings-1.png" alt="DNS wildcard routing setting" className="imagewrapper"/>
</p>

<Note>
    After changing this setting, restart your routing peers and clients to apply it.
</Note>

<Note>
  **Watch out when your infra shares one LoadBalancer IP.** A common K8s deployment pattern (nginx-ingress + path-routing) puts every public hostname under your apex domain — `mgmt`, `dash`, `signal`, `relay`, plus your apps — on a single shared LB IP. When DNS Wildcard Routing is enabled and a client adds a hostname Resource that resolves to that shared IP, the routing peer's NAT rule scopes itself to the resource's domain set. Sibling hostnames sharing the same IP whose firewall behind the LB is stricter (e.g. allow-internal-source-only) may stall on the routing peer because the NAT scope doesn't fire for them.

  Two ways to deal with it: (1) keep DNS Wildcard Routing **disabled**, which falls back to a permissive NAT rule on the routing peer and works as a generic egress for whatever the resource captures; or (2) split your infra so the routed app hostnames live on a different LB IP than the openZro control plane. See [ADR-0015](https://github.com/openzro/openzro/blob/main/docs/adr/0015-hostname-network-resources-and-acl.md) for the full diagnostic and trade-offs.
</Note>
