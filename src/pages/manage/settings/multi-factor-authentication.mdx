# Two-factor authentication (2FA)

openZro has its own two-factor authentication, built into the management
server. It works the same in every self-hosted deployment and needs no
external service. Users add openZro to an authenticator app (Google
Authenticator, Authy, 1Password, Bitwarden, …) and enter the 6-digit code it
shows.

The second factor protects two things:

- **Dashboard and API sessions.** A user the rule applies to enters a code
  after signing in, and again when that session's 2FA expires.
- **Device sign-in**, when you switch it on. Adding a device, or signing one in
  again after its login expired, needs an approval made with the user's code.
  See [2FA on device sign-in](#2-fa-on-device-sign-in).

Personal access tokens and service users are not asked for a code.

## How the second factor works

- **Codes** are standard TOTP (RFC 6238): 6 digits, a new one every 30
  seconds. Each code works only once, so a code seen over someone's shoulder
  cannot be replayed.
- **Backup codes.** Setting up 2FA gives the user 10 single-use backup codes.
  Any of them works in place of a code, for example after losing the phone.
- **Lockout.** After 5 wrong codes in a row, the user is locked out of 2FA
  for 15 minutes.
- **Sessions.** A successful code covers the dashboard session it was entered
  in for up to 8 hours. A new sign-in, or a session on another device, asks
  again.

## Require 2FA

In the dashboard, go to **Settings → Authentication** and find the
**Two-factor authentication (TOTP)** card. There are two rules, chosen by how
the user signs in:

| Setting | Applies to |
| --- | --- |
| **Require 2FA for local accounts** | Users of the bundled Dex local login (email and password). These have no other second factor, so this is the main protection for them. |
| **Require 2FA for federated accounts (redundancy)** | Users who sign in through an external identity provider (Google, Microsoft, Okta, …). They then enter two codes: the provider's and openZro's. Turn this on only if you treat the identity provider as a separate trust domain. |

Under each rule, the card shows how many active users it applies to have no
2FA yet. These are the users who will be asked to set it up at their next
sign-in.

Both rules are off by default. Users can still set up 2FA on their own while
the rules are off.

## Set up 2FA

A user the rules apply to is taken to the setup page at their next sign-in.
Any user can also set it up, or manage it later, from **Profile Settings →
Two-factor authentication** in the account menu.

1. Scan the QR code with the authenticator app, or choose **Can't scan?** to
   type the key in.
2. Enter the 6-digit code the app shows.
3. Save the 10 backup codes somewhere safe, such as a password manager. They
   are shown only once.

From the same section a user can choose **Regenerate backup codes**, which
invalidates the old ones, or **Disable 2FA**. Both require a session verified
with 2FA; if yours isn't, you're asked for a code first. Disabling it under an enforced rule only means setting it up again at
the next sign-in.

## Manage users' 2FA

The **Users** list has a **2FA** column for each user:

- **On**: the user has set up 2FA.
- **Off**: the user has not set up 2FA.
- **Locked until HH:MM**: the user hit the lockout and can try again at that
  time.

To remove a user's second factor, for example after they lost both the
authenticator and the backup codes, open the user's row menu (**⋮**) and
choose **Reset 2FA** (shown only for users who have 2FA set up). The user sets it up again at their next
sign-in. You must have 2FA set up on your own account, and a session verified with it, to reset someone else's.

<p>
    <img src="/docs-static/img/manage/settings/mfa/2fa-users-reset.png" alt="Users list with the 2FA column and the Reset 2FA action" className="imagewrapper"/>
</p>

Turning 2FA off and resetting it are recorded in the activity log. For a
reset, the log records the admin who did it and the user it was done to.

<Note>
    Keep at least two administrators with 2FA set up, so one can reset the
    other's second factor.
</Note>

## 2FA on device sign-in

With **Require 2FA to sign in devices** on, a user the rules above apply to
must approve a device sign-in with their second factor when they:

- add a new device;
- sign a device in again after its login expired (see
  [peer session expiration](/manage/settings/enforce-periodic-user-authentication)).

A device whose login is still valid reconnects in the background without a
code. With login expiration on, the code is therefore asked once per expiration
period.

This stops a leaked password from being enough to bring up a tunnel: the
attacker also needs the user's authenticator.

### What the user sees

1. The user signs in as usual (`openzro up`, or **Connect** in the desktop
   app) and completes the identity provider's login.
2. The client shows a link to approve the sign-in:
   - the CLI prints it and opens it in the browser, unless `--no-browser` is
     set;
   - the desktop app shows it in a window.

   ```text
   This sign-in needs your 2FA approval. Open this link to approve it:
   https://dashboard.example.com/mfa/peer-login#t=…
   The request expires in 5 minutes. Waiting for the approval...
   ```
3. The approval page, which needs no dashboard session, shows the request:
   - the device name and operating system, as the device reported them;
   - the address and location the server saw;
   - a short fingerprint of the device key;
   - the time of the attempt;
   - the account, and the user's email partly masked.
4. The user enters a code from the authenticator app, or a backup code, and
   chooses **Approve**. The device connects on its own within a few seconds.

<p>
    <img src="/docs-static/img/manage/settings/mfa/device-signin-approval.png" alt="Device sign-in approval page" className="imagewrapper"/>
</p>

A request can be approved for 5 minutes. If it was not the user's attempt,
**Not me** denies it, and that device cannot ask again until the request
expires.

The client explains the other outcomes:

- **Denied**: when the device can try again.
- **No 2FA set up**: the user must set it up in the dashboard first. The client
  links to it.
- **Too many requests**: a user can have at most 5 requests at a time, so a
  stolen password cannot flood them with approval links. The client says when
  to try again.

### Before you switch it on

The server enforces this setting, and older clients cannot complete the
approval. Switch it on in this order:

1. **Turn on [peer approval](/manage/peers/approve-peers) for third parties.**
   Put your internal groups in **Groups that skip approval**, so only external
   users' new devices wait for an admin. Keep it on afterwards: 2FA setup is
   self-service, so someone holding only a password could set up their own
   authenticator, but their new device would still wait for an admin.
2. **Make sure everyone the rules apply to has set up 2FA.** Saving the setting
   is refused while an active user it would apply to has no 2FA. The counts
   under the 2FA rules show who is left. Users created or reset later are not
   blocked by this check: they are asked to set up 2FA when they first sign
   in a device.
3. **Upgrade every management server.** A server without this feature would
   let a device sign in without the code.
4. **Upgrade the desktop and CLI clients of the users it applies to.** Older
   clients get a message asking them to update and cannot sign in devices.
   Mobile clients do not support device sign-in approval yet. Do not switch
   this on for accounts whose users rely on them.
5. **Switch on Require 2FA to sign in devices.**

To roll back, switch the setting **off before** bringing back an older
management server.

<Warning>
    The approval link carries a short-lived token that lets whoever holds it
    approve or deny that one sign-in. Users should open it only for a sign-in
    they started, and choose **Not me** otherwise.
</Warning>

### Configure the dashboard URL

Approval and setup links point to the dashboard. If the dashboard is not served
at the management server's address, set its public URL on the management
server, in either of these places:

- `HttpConfig.DashboardURL` in `management.json`;
- the `OPENZRO_DASHBOARD_URL` environment variable, which takes precedence.

The URL must use `https://`. Plain `http://` is accepted only for `localhost`
or a loopback address, for testing, because the page carries a token and the
user's code. The management server refuses to start with any other value.
When it is not set, clients build the link from their management server's
host.

### Troubleshooting

- **The user lost their authenticator.** They can sign in with a backup code
  and set 2FA up again from Profile Settings. Without backup codes, an admin
  uses **Reset 2FA**, and the user sets it up at their next sign-in.
- **"Locked until …"** in the Users list: the user entered 5 wrong codes. Wait
  until the time shown, or reset their 2FA.
- **The client asks to set up 2FA first.** The user has no second factor yet,
  for example a user created or reset after you switched the setting on. They
  set it up in the dashboard, then sign in again.
- **The link opens the wrong host.** Set the
  [dashboard URL](#configure-the-dashboard-url).
- **An older client keeps saying "update openZro".** It cannot complete the
  approval; upgrade it.

### Monitoring

The activity log records:

- each device sign-in that waits for approval, and each approval, wrong code,
  denial and expiry;
- switching the setting on and off.

Through the management metrics endpoint:

| Metric | Meaning |
| --- | --- |
| `management.peer.login.mfa.refusal.counter` | Sign-ins refused by the check, by `reason`: `required` (each poll while waiting), `denied`, `rate_limited`, `enrollment_required`, `error`. |
| `management.peer.login.mfa.outcome.counter` | Approval requests by `outcome`: `approved`, `failed`, `denied`, `expired`. |
| `management.peer.login.mfa.time.to.approval.ms` | Time from a sign-in's first refusal to its approval. |

The design is recorded in
[ADR-0028](https://github.com/openzro/openzro/blob/main/docs/adr/0028-mfa-on-peer-login.md).
