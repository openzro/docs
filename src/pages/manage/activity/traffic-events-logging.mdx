# Traffic Events Logging

Traffic events record the connections that go through your openZro network: who opened a connection to what, on which
protocol and port, whether it was allowed or blocked, which policy allowed it, and how much data it carried. Use them
for audits, troubleshooting and checking that your access policies match real traffic.

Peers report the events to the management server. The management server stores them, shows them in the dashboard and
can export them to your SIEM or to object storage.

## How traffic events are captured

### Where the events come from

The openZro client captures connections in one of two ways, depending on how it runs:

| Client | Capture mechanism |
|---|---|
| **Linux with kernel WireGuard** | The kernel's **conntrack** connection tracker, the same one `iptables` and `nftables` use. Only connections that go through the openZro tunnel are reported. |
| **macOS, Windows, Linux in userspace mode, netstack** | The **userspace packet filter** that processes every tunnel packet. |

Both produce the same event format, so the dashboard and exports look the same whatever the peer's operating system.

### Peer-to-peer connections

When two peers connect directly, both report the connection. For example, when a user opens a CRM server that runs the
openZro client from their laptop on TCP port 443, the laptop reports that it started the connection and the CRM server
reports that it received it. If a policy does not allow the connection, the CRM server reports a blocked event.

### Connections to network resources

When a peer connects to a [network resource](/manage/networks#resources), the peer that opened the connection and the
[routing peer](/manage/networks#routing-peers) that forwards it both report it. The resource itself does not run the
openZro client, so it reports nothing. If the connection is not allowed, the routing peer reports the blocked event.

</p>

## Enable traffic events

Traffic events are off by default. To turn them on:

1. Go to **Settings → Networks**.
2. In the **Network traffic events** card, turn on **Enable network traffic events**.
3. Optionally, turn on **Count bytes and packets**. This enables kernel connection accounting on the peers, so events
   from Linux peers with kernel WireGuard carry the bytes and packets transferred; without it, their traffic volume is
   zero. Peers that filter traffic in userspace always count. It costs a little CPU per connection.

<p>
    <img src="/docs-static/img/manage/activity/traffic-events-logging/traffic-events-logging-settings.png" alt="Network traffic events settings" className="imagewrapper-big"/>
</p>

In the same card you can:

- **Limit to specific groups**: select groups and click **Save filter** to collect events only from peers in those
  groups. With no group selected, every peer reports events.
- Choose the **Default time range on Flow Traffic**, the date filter the Flow Traffic page starts with.

<Note>
    The management server only keeps traffic events when a flow events store is configured. Without one, peers still
    report events and [exports](#export-traffic-events) still receive them, but the Flow Traffic page and the API have
    nothing to show. See [Storage and retention](#storage-and-retention).
</Note>

## View traffic events

Go to **Identity → Flow Traffic**. Each row is one event, with its **Source**, **Destination**, **Protocol & Port**,
**Traffic** volume and **Status**. Events that belong to the same connection are grouped together.

<p>
    <img src="/docs-static/img/manage/activity/traffic-events-logging/flow-traffic.png" alt="Flow Traffic page" className="imagewrapper-big"/>
</p>

Use the search box to find events by peer, IP address or policy, and narrow them down by date range and peer.

Events usually appear within a minute. A connection's end event is reported when the connection closes, so for
long-lived TCP connections it can arrive much later than the start event.

## Read and correlate events

Every event has a type:

| Type | Meaning |
|---|---|
| `start` | A connection was opened. |
| `end` | A connection was closed. For UDP and ICMP, which have no closing handshake, this happens after a period of inactivity. |
| `drop` | A connection was blocked by the reporting peer's access rules. |

Each peer reports the connection from its own point of view, so one connection produces up to four events. For
example, when peer A opens a TCP connection to peer B and it is allowed, you see a `start` and an `end` event from
each of them. Match them with the source port, which is the same in all four.

If peer B blocks the connection, peer A still reports `start` and `end` events, because it does not know the
connection was blocked, and peer B reports one or more `drop` events, one for each retry the application on peer A
makes.

<Note>
    Blocked (`drop`) events are only reported by peers that filter traffic in userspace: macOS, Windows, netstack mode
    and Linux in userspace mode. A Linux peer with kernel WireGuard blocks the traffic but does not report it. To get
    blocked events from a Linux peer, run it with `OZ_WG_KERNEL_DISABLED=true` and `OZ_FORCE_USERSPACE_ROUTER=true`
    (see [client environment variables](/client/environment-variables)).
</Note>

## Event data

Each event contains:

- **Timestamps**: when the event happened on the peer, and when the management server received it.
- **Flow ID**: shared by the events of one connection, as seen by one peer.
- **Type**: `start`, `end` or `drop`.
- **Direction**: `ingress` or `egress`, from the point of view of the reporting peer.
- **Protocol**, **source and destination IP addresses**, and **ports** for TCP and UDP or **ICMP type and code**.
- **Volume**: packets and bytes received and sent, when **Count bytes and packets** is on.
- **Rule ID**: the policy that allowed the connection.
- **Resource IDs**: the network resource or route the connection was going to or coming from, when there is one.

The API serves the events at `GET /api/network-traffic-events`. It returns up to 50,000 events per request and accepts
these query parameters: `peer_id`, `source_ip`, `dest_ip`, `source_port`, `dest_port`, `protocol`, `type`,
`direction`, `rule_id`, `since` and `until` (RFC 3339 timestamps), `limit` and `offset`.

## Storage and retention

Persistence is off by default. To store traffic events, set `OPENZRO_FLOW_STORE_ENGINE` (`postgres`, `mysql` or
`sqlite`) and `OPENZRO_FLOW_STORE_DSN` on the management server.

Events are kept for 7 days by default; set `OPENZRO_FLOW_RETENTION` (for example `720h` for 30 days) to change it. A
cleanup runs once a day. On PostgreSQL, events are stored in monthly partitions and old partitions are dropped; on
MySQL and SQLite, old rows are deleted.

For the full setup, see [Flow Events Store](/selfhosted/flow-events-store).

## Export traffic events

You can send traffic events to other systems as well as, or instead of, storing them:

| Destination | Use |
|---|---|
| **Elasticsearch** | Search and dashboards in your SIEM. |
| **Datadog** | Logs and Cloud SIEM. |
| **HTTP** | Any other receiver, such as Splunk HEC or Vector. |
| **Amazon S3** (or S3-compatible) | Long-term archive. |
| **Google Cloud Storage** | Long-term archive. |

Configure exports in the dashboard under **System → Integrations → Flow Exports** with **Add destination**, or with
`OPENZRO_FLOW_EXPORT_*` (Elasticsearch, Datadog, HTTP) and `OPENZRO_FLOW_ARCHIVE_*` (S3, GCS) environment variables on
the management server. Archives are written as NDJSON by default, or as Parquet with
`OPENZRO_FLOW_ARCHIVE_FORMAT=parquet`.

For archive setup, see [Flow archive on GCS](/selfhosted/flow-archive-gcs) and
[Flow archive compaction](/selfhosted/flow-archive-compaction).

<Note>
    Flow exports carry traffic events. To stream the audit log (configuration changes, logins), use the
    [Activity Streamer](/manage/activity/event-streaming).
</Note>
