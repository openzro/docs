# DNS Aliases for Routed Networks

This guide explains how to use Custom DNS Zones with openZro's Networks to provide easy-to-remember DNS names for resources in private
networks.


Custom DNS Zones work seamlessly with openZro's [Networks](/manage/networks) feature to provide friendly DNS names for resources behind routing peers. This eliminates the need to remember IP addresses when accessing private network resources, creating a professional enterprise-like experience.

## How It Works

### The Challenge

Imagine you're a developer who needs to connect to a PostgreSQL database in your company's data center. The database is at IP address `192.168.0.68`, accessible through an openZro routing peer. You might write connection strings like this:

```bash
psql -h 192.168.0.68 -U admin
```

This works, but it's problematic:
- **Hard to remember**: Which IP is the database? Which is the API? Which is staging vs. production?
- **Difficult to update**: If the database moves to a new IP, every developer needs to update their configurations
- **Not team-friendly**: New team members need to maintain a list of IP addresses for internal services

### The Solution

DNS Aliases with Custom DNS Zones solve this by giving your private network resources friendly, memorable DNS names. Instead of `192.168.0.68`, your developers connect to `postgres.openzro.internal` or simply `postgres`.

### How the DNS Resolution Works

Here's what happens when you set up a DNS Alias and a developer tries to connect to `postgres.openzro.internal`:

**Setup (One-Time):**

1. **Admin creates a Custom DNS Zone** called `openzro.internal` in the openZro dashboard
2. **Admin adds an A record**: `postgres` → `192.168.0.68` (the actual database IP on the private network)
3. **Zone is distributed** to the developer's distribution group (e.g., dev)

**When a developer connects:**

1. **Developer's laptop** queries `postgres.openzro.internal`
2. **openZro's DNS resolver** on the laptop receives the query
3. **Custom Zone record is matched**: openZro finds the A record: `postgres.openzro.internal` → `192.168.0.68`
4. **DNS response returned**: The IP `192.168.0.68` is returned to the application
5. **Routing kicks in**: Traffic to `192.168.0.68` is automatically routed through the openZro routing peer that has access to the `192.168.0.0/24` network
6. **Connection established**: The application connects successfully to the database

## Step-by-Step Guide

This guide will walk you through a common use case: providing DNS names for a PostgreSQL database and an internal wiki hosted in a private data center.

**Network Setup:**

- **openZro Peers**: Devices organized into groups, such as a `dev` for developers.
- **Routing Peer**: A gateway server in the data center.
- **Private Network**: Subnet `192.168.0.0/24` with internal services:
  - PostgreSQL Database: `192.168.0.68`
  - Internal Wiki: `192.168.0.78`

### Step 1: Create a Custom DNS Zone

First, create a Custom DNS Zone to manage the DNS records for your private services. See
[Custom Zones](/manage/dns/custom-zones) for the dialog in detail.

1. Go to **DNS**, open the **DNS Zones** tab and click **Add Zone**.
2. On the **Zone** tab:
   - **Name**: `Internal services`
   - **Domain**: `openzro.internal`
   - **Append to search domain**: turn it on to allow short names (e.g., `postgres` instead of
     `postgres.openzro.internal`).
3. Click **Continue** and select the **Distribution Groups** that should resolve these names (e.g., `dev`).
4. Click **Add Zone**.

### Step 2: Add DNS Records

Open the zone and click **Add Record** for each service:

| Type | Name | Content |
|---|---|---|
| A | `postgres` | `192.168.0.68` |
| A | `wiki` | `192.168.0.78` |

### Step 3: Configure Network Routing

The DNS records return private IPs, so peers also need a route to those IPs through a routing peer.

#### Create a Network

1. Go to **Networks** and click **Add Network**.
2. Name it `Internal Network`, add a description, and click **Add Network**.

#### Add Network Resources

Add the services as **IP resources** (or the whole `192.168.0.0/24` subnet as one resource). On the network's
**Resources** tab, click **Add Resource**:

- **Name**: `Internal Postgres`, **Address**: `192.168.0.68`, **Destination Groups**: `internal-services`
- **Name**: `Internal Wiki`, **Address**: `192.168.0.78`, **Destination Groups**: `internal-services`

<Note>
    Use the IP addresses, not the zone names. A domain resource for a name that the custom zone already answers would
    never be routed, because the zone answers the query before the domain route is installed.
</Note>

#### Create an Access Control Policy

Click **Add Policy** on one of the resources and allow the `dev` group to reach `internal-services` over TCP (all
ports, or only the ones your services use). Click **Continue** twice, name it `Internal Services Policy`, and click
**Add Policy**.

#### Add a Routing Peer

On the **Routing Peers** tab, click **Add Routing Peer**, select the peer (or peer group) that runs in your data
center, click **Continue** and then **Add Routing Peer**.

The network is now configured:

<img src="/docs-static/img/manage/dns/dns-aliases/network-overview.png" alt="Internal Network with the two IP resources" className="imagewrapper-big"/>

### Step 4: Verify the Setup

With the DNS zone and records configured, your developers can now access the services using the friendly DNS names.

#### Verify Network Routes

First, confirm that peers in the `dev` group have received the routes to the two services.

On a peer device in the `dev` group, run:

```bash
openzro networks ls
```

You should see output similar to:

```bash
Available Networks:

  - ID: Internal Postgres
    Network: 192.168.0.68/32
    Status: Selected

  - ID: Internal Wiki
    Network: 192.168.0.78/32
    Status: Selected
```

#### Access Your Services

Now your developers can access the services using DNS names:

```bash
# Connect to the database using full DNS name
psql -h postgres.openzro.internal -U admin

# Access the internal wiki using full DNS name
curl http://wiki.openzro.internal
```

With search domain enabled, you can use short names:

```bash
# Connect to the database
psql -h postgres -U admin

# Access the internal wiki
curl http://wiki
```

## Benefits

- **Simplified Access**: No more memorizing IP addresses.
- **Centralized Management**: Update IP addresses in one place without affecting clients.
- **Improved Security**: Isolate environments and teams with separate zones and distribution groups.
- **Enhanced Productivity**: Developers can discover and connect to services faster.

## Advanced Use Cases

### Environment Separation

You can create separate DNS zones for different environments (e.g., production, staging) to isolate resources.

- **Production**:
  - Network routing to `10.0.1.0/24`.
  - DNS zone `prod.openzro.internal` distributed to the `SRE Team`.
- **Staging**:
  - Network routing to `10.0.2.0/24`.
  - DNS zone `staging.openzro.internal` distributed to `Developers` and `QA`.

### Multi-Site Architecture

For organizations with multiple data centers, you can create separate networks and DNS zones for each location.

- **US East**:
  - Network to `10.1.0.0/16`.
  - DNS zone `us-east.openzro.internal` for the `US Team`.
- **EU West**:
  - Network to `10.2.0.0/16`.
  - DNS zone `eu-west.openzro.internal` for the `EU Team`.

### Failover and Load Balancing

Use CNAME records to create aliases that can be quickly updated during failover scenarios without requiring changes to client configurations.
