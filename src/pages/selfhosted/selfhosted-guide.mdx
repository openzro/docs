# Advanced guide

openZro is open-source and can be self-hosted on your servers.

It relies on components developed by openZro Authors [Management Service](https://github.com/openzro/openzro/tree/main/management), [Management UI Dashboard](https://github.com/openzro/openzro/tree/main/dashboard), [Signal Service](https://github.com/openzro/openzro/tree/main/signal),
a 3rd party open-source STUN/TURN service [Coturn](https://github.com/coturn/coturn), and an identity provider (IDP).

If you would like to learn more about the architecture please refer to the [architecture section](/about-openzro/how-openzro-works).


<Note>
**New to self-hosting?** The [Quickstart guide](/selfhosted/selfhosted-quickstart) uses the built-in identity provider and is the fastest way to get started. This advanced guide is for users who need to integrate with an existing IdP or have specific enterprise requirements.
</Note>


## When to use this guide

Use this advanced guide if you:

- Need to integrate with an **existing identity provider** (Okta, Azure AD, Auth0, etc.)
- Require **SCIM provisioning** for user/group sync
- Have **compliance requirements** that mandate a specific IdP
- Want **full control** over the authentication infrastructure

For simpler deployments, the [Quickstart with embedded IdP](/selfhosted/selfhosted-quickstart) is recommended.

## Advanced self-hosting guide with a custom identity provider

### Requirements

- Virtual machine offered by any cloud provider (e.g., AWS, DigitalOcean, Hetzner, Google Cloud, Azure ...).
- Any Linux OS.
- Docker Compose installed (see [Install Docker Compose](https://docs.docker.com/compose/install/)).
- [jq](https://jqlang.github.io/jq/) installed. In most distributions usually available in the official repositories and can be installed with `sudo apt install jq` or `sudo yum install jq`
- Domain name pointing to the public IP address of your server.
- **Firewall ports** (see below for your setup type).
- Maybe a cup of coffee or tea :)

#### Port requirements

The default stack publishes these ports:

| Port | Protocol | Description |
|------|----------|-------------|
| 80, 443 | TCP | Dashboard and Let's Encrypt (the dashboard container obtains the certificate) |
| 33073 | TCP | Management API and gRPC (`OPENZRO_MGMT_API_PORT`) |
| 10000 | TCP | Signal gRPC (`OPENZRO_SIGNAL_PORT`) |
| 33080 | TCP | Relay, WebSocket and QUIC (`OPENZRO_RELAY_PORT`) |
| 3478 | UDP | Coturn STUN/TURN |
| 49152-65535 | UDP | Coturn TURN relay range |

To serve everything on 443 instead, put openZro behind your own reverse proxy; see
[Running openZro behind an existing reverse proxy](#advanced-running-open-zro-behind-an-existing-reverse-proxy).

For this tutorial we will be using the domain ```openzro.example.com```, which points to an Ubuntu machine.

### Step 1: Get the openZro code

```bash
# Pick a release tag from https://github.com/openzro/openzro/releases
TAG=v0.53.1-alpha.103
git clone --depth 1 --branch $TAG https://github.com/openzro/openzro.git
```

All current releases are prereleases, so `releases/latest` does not resolve to one; pick the tag explicitly.

Then switch to the infra folder that contains docker-compose file:

```bash
cd openzro/infrastructure_files/
```
### Step 2:  Prepare configuration files

To simplify the setup we have prepared a script to substitute required properties in the [docker-compose.yml.tmpl](https://github.com/openzro/openzro/tree/main/infrastructure_files/docker-compose.yml.tmpl) and [management.json.tmpl](https://github.com/openzro/openzro/tree/main/infrastructure_files/management.json.tmpl) files.

The [setup.env.example](https://github.com/openzro/openzro/tree/main/infrastructure_files/setup.env.example) file contains multiple properties that have to be filled. You need to copy the example file to `setup.env` before updating it.

```bash
## example file, you can copy this file to setup.env and update its values
##
# Dashboard domain. e.g. app.mydomain.com
OPENZRO_DOMAIN=""
# OIDC configuration e.g., https://example.eu.auth0.com/.well-known/openid-configuration
OPENZRO_AUTH_OIDC_CONFIGURATION_ENDPOINT=""
OPENZRO_AUTH_AUDIENCE=""
# e.g. openzro-client
OPENZRO_AUTH_CLIENT_ID=""
# required with an external IdP, e.g. "openid profile email offline_access"
OPENZRO_AUTH_SUPPORTED_SCOPES=""
# indicates whether to use Auth0 or not: true or false
OPENZRO_USE_AUTH0="false"
OPENZRO_AUTH_DEVICE_AUTH_PROVIDER="none"
# enables Interactive SSO Login feature (Oauth 2.0 Device Authorization Flow)
OPENZRO_AUTH_DEVICE_AUTH_CLIENT_ID=""
# e.g. hello@mydomain.com
OPENZRO_LETSENCRYPT_EMAIL=""
```

This is an excerpt; `setup.env.example` documents every variable, including the embedded Dex settings and
`OPENZRO_DISABLE_LETSENCRYPT`.

<Note>
    The changes made to `setup.env` will not take any effect until you run `configure.sh` (mentioned later on).
</Note>

- Set ```OPENZRO_DOMAIN``` to your domain, e.g. `openzro.example.com`
- Configure ```OPENZRO_LETSENCRYPT_EMAIL``` property.
This can be any email address. [Let's Encrypt](https://letsencrypt.org/) will create an account while generating a new certificate.

<Note>
    openZro supports automatic renewal by default when using Let's Encrypt.
</Note>

<Note>
    If you want to setup openZro with your own reverse-Proxy and without using the integrated letsencrypt, follow [this step here instead](#advanced-running-open-zro-behind-an-existing-reverse-proxy).
</Note>

### Step 3: Configure Identity Provider (IDP)

openZro supports generic OpenID (OIDC) protocol allowing integration with any IDP following the specification.

openZro's management service integrates with some of the most popular IDP APIs, allowing the service to cache and display user names and email addresses without storing sensitive data.

Pick the one that suits your needs, follow the **Standalone Setup (Advanced)** section in each guide, and continue with this guide:

**Self-hosted options**
- [Zitadel](/selfhosted/identity-providers/zitadel) - Previously used in the quickstart script
- [Keycloak](/selfhosted/identity-providers/keycloak) - Popular open-source IAM
- [Authentik](/selfhosted/identity-providers/authentik) - Flexible open-source IdP
- [PocketID](/selfhosted/identity-providers/pocketid) - Lightweight self-hosted option

**Managed options**
- [Microsoft Entra ID](/selfhosted/identity-providers/managed/microsoft-entra-id) - Azure AD / Microsoft 365
- [Google Workspace](/selfhosted/identity-providers/managed/google-workspace) - Google accounts
- [Okta](/selfhosted/identity-providers/managed/okta) - Enterprise SSO
- [Auth0](/selfhosted/identity-providers/managed/auth0) - Flexible auth platform
- [JumpCloud](/selfhosted/identity-providers/managed/jumpcloud) - Cloud directory

<Note>
Each provider page includes both "Management Setup (Recommended)" (for use with the embedded IdP) and "Standalone Setup (Advanced)" sections. For this guide, follow the **Standalone Setup (Advanced)** section.
</Note>

### Step 4: Disable single account mode (optional)

openZro Management service runs in single account mode by default.
Single account mode ensures that all the users signing up for your self-hosted installation will join the same account/network.
In most cases, this is the desired behavior.

If you want to disable the single-account mode, set `--disable-single-account-mode` flag in the
[docker-compose.yml.tmpl](https://github.com/openzro/openzro/tree/main/infrastructure_files/docker-compose.yml.tmpl)
`command` section of the `management` service.

### Step 5: Run configuration script
Make sure all the required properties set in the ```setup.env``` file and run:

```bash
./configure.sh
```

This will export all the properties as environment variables and generate, under `artifacts/`:
`docker-compose.yml`, `management.json`, `turnserver.conf`, `dex.config.yaml`, the `grpc-certs/` used between
management and Dex, the Dex theme under `web/themes/`, and, with an external IdP, `openid-configuration.json`.

<Note>
    The changes made to `setup.env` will not take any effect until you run `configure.sh` again
</Note>

<Note>
For detailed documentation of all configuration file options, see the [Configuration Files Reference](/selfhosted/configuration-files).
</Note>

### Step 6: Run docker compose:

```bash
cd artifacts
docker compose up -d
```
### Step 7: Check docker logs (Optional)

```bash
cd artifacts
docker compose logs signal
docker compose logs management
docker compose logs coturn
docker compose logs relay
docker compose logs dashboard
docker compose logs dex
```

## Advanced: Running openZro behind an existing reverse-proxy

If you already have a reverse proxy (Nginx, Caddy, Traefik, etc.), you can put openZro behind it instead of letting the dashboard container obtain certificates itself.

<Note>
Not all reverse proxies are supported as openZro uses *gRPC* for various components. Your reverse proxy must support HTTP/2 and gRPC proxying.
</Note>

Set `OPENZRO_DISABLE_LETSENCRYPT=true` in `setup.env` and run `./configure.sh`; it prints the routes your proxy must
forward.

See the [External Reverse Proxy Configuration](/selfhosted/external-reverse-proxy) page for:
- Complete configuration templates for [Traefik](/selfhosted/external-reverse-proxy#traefik), [Nginx](/selfhosted/external-reverse-proxy#nginx), [Caddy](/selfhosted/external-reverse-proxy#caddy), and [Nginx Proxy Manager](/selfhosted/external-reverse-proxy#nginx-proxy-manager)
- Required routing endpoints and port mappings
- Docker Compose examples for external proxies
- Troubleshooting tips

## Advanced: Additional configurations for cloud providers

### Hetzner
Hetzner uses stateless [firewall](https://docs.hetzner.com/robot/dedicated-server/firewall/), which means it doesn't "keep track of" whether or not an incoming packet belongs to an established connection. In this case, you may add to this server firewall an UDP port range equals to the result of:
```bash
sudo cat /proc/sys/net/ipv4/ip_local_port_range
```

### Oracle Cloud Infrastructure (OCI)
Linux images provided by Oracle Cloud includes some default [firewall rules](https://docs.oracle.com/en-us/iaas/Content/Compute/References/bestpracticescompute.htm#Essentia) which block ingress UDP on port 3478. This is required by Coturn without which only peers in same LAN would be able to communicate with each other but not peers on different networks. Besides opening the [required ports](#port-requirements) on _Security Rules_, you also need to run below command on the virtual machine.
```bash
sudo iptables -I INPUT -p udp -m udp --dport 3478 -j ACCEPT
```
<Note>
Oracle Cloud discourages use of UFW. You will have to use IPTABLES.
</Note>

## Backup
To backup your openZro installation, you need to copy the configuration files, and the Management service databases.

The configuration files are located in the folder where you ran the installation script. To backup, copy the files to a backup location:
```bash
cd openzro/infrastructure_files/artifacts/
mkdir backup
cp -r docker-compose.yml turnserver.conf management.json dex.config.yaml grpc-certs backup/
# with an external IdP, also: cp openid-configuration.json backup/
```

To save the Management service databases, you need to stop the Management service and copy the files from the store directory using a docker compose command as follows:
```bash
docker compose stop management
docker compose cp -a management:/var/lib/openzro/ backup/
docker compose start management
```

The embedded Dex keeps its own database in the `openzro-dex` volume (`/var/lib/dex` in the `dex` container); back it
up the same way with `docker compose cp -a dex:/var/lib/dex/ backup/dex/`.

## Upgrade

To upgrade openZro to the latest version, you need to review the [release notes](https://github.com/openzro/openzro/releases) for any breaking changes and follow the upgrade steps below:
1. Run the backup steps described in the [backup](#backup) section.
2. Pull the latest openZro docker images:
   ```bash
   cd openzro/infrastructure_files/artifacts/
   docker compose pull
    ```
3. Restart the openZro containers with the new images:
   ```bash
   docker compose up -d --force-recreate
    ```

## Migrating to Embedded IdP

If you've deployed openZro using this advanced guide and want to simplify your setup by migrating to the embedded IdP:

1. Your existing IdP can be added as an embedded IdP directly in the openZro Management Dashboard
2. Users can continue logging in with their existing credentials
3. You can gradually transition to local user management

See the [Migration Guide](/selfhosted/identity-providers#migration-guide-and-backwards-compatibility) for detailed instructions.
