# Troubleshooting

This page will help with various issues when self-hosting openZro.

## Identity provider Issues

### I lost the bootstrap admin credentials

**Problem**: The install script printed admin credentials but you
didn't save them, and the terminal session is gone.

**Solutions**:
- If you used the [Zitadel-based install
  script](/selfhosted/selfhosted-quickstart): open Zitadel's own
  admin console at `https://<your-domain>/ui/console` and use
  the password-recovery flow (requires SMTP configured in
  Zitadel).
- For the embedded Dex IdP: generate a bcrypt hash with
  `docker run --rm ghcr.io/dexidp/dex:<tag> dex hash-password '<new password>'`,
  set it as `OPENZRO_DEX_ADMIN_PASSWORD_BCRYPT` in `setup.env`, re-run
  `./configure.sh` and run `docker compose restart dex`. Before
  re-running `configure.sh`, copy `artifacts/management.json` to the
  `infrastructure_files` directory so the datastore encryption key is
  kept ([openzro#247](https://github.com/openzro/openzro/issues/247)).
- If neither path works, redeploy from scratch:
  `docker compose down -v` removes the volumes, then re-run the
  install script for a fresh admin.

### A user can't sign in via the IdP

**Problem**: Sign-in flow loops back to the IdP login page or
fails with an OIDC error.

**Solutions**:
- Verify the redirect URIs configured in the IdP exactly match
  `https://<your-domain>/auth` and `https://<your-domain>/silent-auth`
  (no trailing slash, exact protocol).
- Verify the IdP's issuer URL matches `OPENZRO_AUTH_AUTHORITY` in
  `setup.env`, which `configure.sh` writes to `HttpConfig.AuthIssuer`
  in `management.json`.
- Check the IdP's logs for "consent required" or "scope mismatch"
  errors. With the embedded Dex, openZro requests
  `openid profile email offline_access groups`; with an external IdP,
  the scopes in `OPENZRO_AUTH_SUPPORTED_SCOPES`.

### SSO connector not appearing on login page

**Problem**: You configured an identity provider but it doesn't show on the login page.

**Solutions**:
1. Verify the connector was saved: go to **Settings** → **Auth Providers**
2. Check that the redirect URL is correctly configured in your IdP
3. Review Management service logs for configuration errors: `docker compose logs management`
4. Ensure the IdP application has the correct redirect URI from openZro

### "Invalid redirect URI" error from IdP

**Problem**: When clicking an SSO button, the IdP returns an invalid redirect URI error.

**Solutions**:
1. Copy the exact redirect URL from openZro (shown after saving the connector)
2. Add it to your IdP's allowed redirect URIs
3. Check for trailing slashes or typos
4. Some IdPs are case-sensitive

### Auth Providers tab shows an error

**Problem**: **Settings** → **Auth Providers** fails to load or save connectors.

**Solution**: The tab manages connectors in the embedded Dex over gRPC. Check that:
- the `management` service has `OPENZRO_DEX_GRPC_ADDR` and the `OPENZRO_DEX_GRPC_*` certificate paths set, and the
  certificates exist in `artifacts/grpc-certs/` (both are generated by `configure.sh`);
- the `dex` service has `DEX_API_CONNECTORS_CRUD=true`; without it, every call fails with
  "api_connectors_crud feature flag is not enabled".

### Users not syncing from SSO provider

**Problem**: Users who authenticate via SSO don't appear in the user list.

**Solutions**:
- Users appear after their first successful login, not immediately after connector configuration
- Check that the SSO flow completes successfully (user should land on Dashboard)
- Review Management logs for any token validation errors

## Debugging TURN connections

If a peer-to-peer connection is not possible, peers fall back to the openZro Relay or, when one side cannot use it, to the TURN server. If the connection is not possible even with TURN (Relay),
then we need to confirm that your turn configuration is correct and that it is available.

To test your TURN configuration you can access the [online tester](https://webrtc.github.io/samples/src/content/peerconnection/trickle-ice).
There you will find a ICE servers input box, where you can select and remove the existing server, then add your turn server
configuration as follows:

Add your Coturn server as a TURN server, with the URL `turn:<your-domain>:3478`, the username and the password from
the `TURNConfig` section of `management.json`, then click **Gather candidates**.

Where you have the following types: `host` (local address), `srflx` (STUN reflexive address), `relay`
(TURN relay address). If `srflx` and `relay` are not present then the TURN server is not working or not accessible and you should review the required ports in the [requirements section](/selfhosted/selfhosted-guide#requirements).

## Dashboard Issues

### Dashboard shows blank page

**Problem**: The Dashboard loads but shows a blank page or errors.

**Solutions**:
1. Check browser console for JavaScript errors (F12 → Console)
2. Verify the Dashboard can reach the Management API
3. Check CORS configuration if running behind a custom reverse proxy
4. Clear browser cache and try again

### "Unauthorized" or "403" errors

**Problem**: API calls return unauthorized or forbidden errors.

**Solutions**:
1. Verify your authentication token is valid
2. Check that the user has appropriate permissions
3. For API access, ensure you're using a valid Personal Access Token (PAT)
4. Review Management service logs for detailed error information

## Certificate Issues

### Let's Encrypt certificate not renewing

**Problem**: SSL certificate expires and doesn't auto-renew.

**Solutions**:
1. Ensure port 80 is accessible for ACME challenge
2. Check the dashboard container's logs, which run certbot: `docker compose logs dashboard`
3. Verify the domain points to the correct IP
4. Restart the dashboard to retry: `docker compose restart dashboard`, then restart `management`, which reads the
   same certificate

### Certificate errors with custom reverse proxy

**Problem**: SSL errors when using your own reverse proxy.

**Solutions**:
1. Ensure your reverse proxy terminates SSL correctly
2. Set `OPENZRO_DISABLE_LETSENCRYPT=true` in your configuration
3. Configure proper headers (X-Forwarded-For, X-Forwarded-Proto)
4. Verify HTTP/2 support is enabled for gRPC endpoints

## Connection Issues

### Peers can't connect to each other

**Problem**: Peers are registered but can't establish connections.

**Solutions**:
1. Check that UDP port 3478 (STUN/TURN), the TURN relay port range (UDP 49152-65535 by default) and the relay port (TCP 33080) are reachable
2. Verify the TURN server is working (see [TURN debugging](#debugging-turn-connections))
3. Check firewall rules on both peers
4. Review peer logs: `openzro status -d`

### Management service unreachable

**Problem**: Clients can't connect to the Management service.

**Solutions**:
1. Verify the management port is reachable (`OPENZRO_MGMT_API_PORT`, 33073 by default, or 443 behind a reverse proxy)
2. Check DNS resolution for your domain
3. Review Management logs: `docker compose logs management`
4. Test with curl: `curl -v https://your-domain.com:33073/api/users` should return `401` (no token), which shows the
   API is up

## Database Issues

### Management service won't start after upgrade

**Problem**: After upgrading, the Management service fails to start.

**Solutions**:
1. Check logs for migration errors: `docker compose logs management`
2. Ensure you followed the [upgrade guide](/selfhosted/maintenance/upgrade)
3. Restore from backup if needed
4. For major version jumps, you may need intermediate upgrades

### Data corruption after power loss

**Problem**: Services don't start properly after unexpected shutdown.

**Solutions**:
1. Check for database lock files
2. Review all service logs
3. Consider restoring from backup
4. For SQLite databases, you may need to run integrity checks

## Getting Help

If you're still experiencing issues:

1. **Check logs**: `docker compose logs` for all services
2. **Search existing issues**: [GitHub Issues](https://github.com/openzro/openzro/issues)
3. **Join our community**: [GitHub Discussions](https://github.com/openzro/openzro/discussions)
4. **Open an issue**: Include logs, configuration (without secrets), and steps to reproduce
