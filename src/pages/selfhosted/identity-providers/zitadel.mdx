# Zitadel with openZro Self-Hosted

[Zitadel](https://zitadel.com) is an open-source identity infrastructure platform designed for cloud-native environments. It provides multi-tenancy, customizable branding, passwordless authentication, and supports protocols like OpenID Connect, OAuth2, SAML2, and LDAP.

<Note>
The legacy `getting-started-with-zitadel.sh` installer deploys Zitadel as the IdP. If you have such a deployment, see
[Migrating from the Zitadel installer](#migrating-from-the-zitadel-installer) below.
</Note>

## Management Setup (Recommended)

Add Zitadel as an authentication provider of openZro's embedded Dex from the dashboard. This is the simplest approach and recommended for most deployments.

### Prerequisites

- An openZro self-hosted deployment with the embedded Dex (the default), and the dashboard's
  **Settings → Auth Providers** page working (management needs `OPENZRO_DEX_GRPC_ADDR`; the Docker Compose stack sets
  it)
- Zitadel instance (cloud or self-hosted)

### Step 1: Create a Project in Zitadel

1. Log in to your Zitadel Console
2. If you don't have a project yet, click **New Project** (or navigate to an existing project)

3. Fill in the project details:
   - **Name**: `openZro` (or your preferred name)

4. Click **Create**

1. Make sure you're in your project (select it from the project dropdown if needed)
2. Click **New** in the **Applications** section

2. Click **Create**.

### Step 4: Configure Token Settings in Zitadel

1. Return to the Zitadel Console tab
2. Navigate to your openZro application → **Token Settings**
3. Enable:
   - **Include user's profile info in the ID Token**
   - **User roles inside ID Token** (if group mapping is needed)

<p>
    <img src="/docs-static/img/selfhosted/identity-providers/self-hosted/zitadel/11_token-settings-zitadel.png" alt="Token settings" className="imagewrapper-big"/>
</p>

4. Click **Save**

### Step 5: Add Zitadel in openZro

1. In the openZro dashboard, go to **Settings → Auth Providers** and click **Add provider**.
2. Fill in the form:

| Field | Value |
|-------|-------|
| ID | `zitadel` |
| Type | Generic OIDC |
| Display name | `Zitadel` |
| Issuer URL | Your Zitadel URL, e.g. `https://your-instance.zitadel.cloud` (no trailing slash) |
| Client ID | From Step 3 |
| Client Secret | From Step 3 |
| Redirect URI | Prefilled: `https://<your-domain>/dex/callback` |

3. Click **Add provider**.

<p>
    <img src="/docs-static/img/selfhosted/identity-providers/openzro-add-provider-oidc.png" alt="Add authentication provider dialog" className="imagewrapper-big"/>
</p>

### Step 6: Test the Connection

1. Log out of the openZro dashboard.
2. The sign-in page now shows **Log in with Zitadel**.
3. Click it and authenticate with your Zitadel credentials.
4. You are redirected back to openZro and logged in. A user who logs in for the first time is added to the account
   with the default role.

### Configuring JWT 'groups' Claim

Zitadel uses **roles** instead of groups. By default, Zitadel's role claims use a nested JSON object format, but openZro expects a flat array of strings. You'll need to create a Zitadel Action to transform roles into a `groups` claim.

#### Step 1: Create the Groups Action

1. In Zitadel Console, go to **Actions**
2. Click **New**
3. Fill in:
   - **Name**: `groupsClaim`
4. Add the following script:

```javascript
function groupsClaim(ctx, api) {
  if (ctx.v1.user.grants == undefined || ctx.v1.user.grants.count == 0) {
    return;
  }
  let groups = [];
  ctx.v1.user.grants.grants.forEach(claim => {
    claim.roles.forEach(role => {
      groups.push(role);
    });
  });
  api.v1.claims.setClaim('groups', groups);
}
```

5. Click **Add**

<p>
    <img src="/docs-static/img/selfhosted/identity-providers/self-hosted/zitadel/jwt_create-action.png" alt="Create action" className="imagewrapper-big"/>
</p>

#### Step 2: Configure Action Triggers

1. Go to **Actions** → **Flows**
2. Select **Complement Token**
3. Add triggers for the `groupsClaim` action:
   - **Pre Userinfo creation**
   - **Pre access token creation**

<p>
    <img src="/docs-static/img/selfhosted/identity-providers/self-hosted/zitadel/jwt_add-trigger.png" alt="Add trigger" className="imagewrapper-big"/>
</p>

<p>
    <img src="/docs-static/img/selfhosted/identity-providers/self-hosted/zitadel/jwt_triggers.png" alt="Add trigger" className="imagewrapper-big"/>
</p>

#### Step 3: Assign Roles to Users

1. Go to your **Project** in Zitadel
2. Navigate to **Roles** and create roles (e.g., `admin`, `developer`)
3. Go to **Authorizations** and assign roles to users

<Note>
Dex passes upstream groups on only when its connector sets `insecureEnableGroups: true` and requests the `groups`
scope. Connectors added from **Settings → Auth Providers** do not set these, so the claim does not reach openZro.
To use JWT group sync, declare the connector in `dex.config.yaml` instead (Docker Compose: `artifacts/dex.config.yaml`;
Helm: `dex.config.connectors`), as in the
[Helm quickstart](/selfhosted/kubernetes/helm-quickstart#jwt-group-sync-when-using-an-upstream-id-p).
</Note>

#### Step 4: Enable JWT Group Sync in openZro

1. In openZro Dashboard, go to **Settings** → **Groups**
2. Enable **JWT group sync**
3. Set **JWT claim** to `groups`
4. Optionally configure **JWT allow group** to restrict access

<Note>
The action transforms Zitadel's role structure into a flat array. If you need to include project context, modify the script to use `groups.push(role + ':' + claim.projectId)`.
</Note>

## Standalone Setup (Advanced)

The standalone setup wires Zitadel as openZro's *only* identity
provider — Dex is bypassed (it keeps running but is not used) and the management daemon talks
directly to Zitadel for both token validation and user
lifecycle. Choose this path **only** if all three apply:

1. **Zitadel is the source of truth for user lifecycle.** You
   want openZro to call Zitadel's management API to list,
   invite, and delete users — so deleting a user in openZro
   removes them from Zitadel too. The recommended setup above
   only consumes tokens; it cannot write back.
2. **You need just one IdP, and it's Zitadel.** The standalone
   path doesn't support multiple upstreams — there's no Dex to
   aggregate them.
3. **You're willing to give up the bootstrap admin fallback.** No
   embedded local user store. If Zitadel is down or
   misconfigured, nobody can log into the dashboard.

For everyone else — multi-IdP shops, anyone wanting a static
admin fallback, or operators who only need authentication (not
user lifecycle writeback) — stick with the
[Management Setup (Recommended)](#management-setup-recommended)
above.

For detailed standalone instructions, see
[Zitadel SSO with openZro Self-Hosted (Advanced)](/selfhosted/identity-providers/advanced/zitadel).

<Note>
If you prefer not to self-host, Zitadel offers a managed cloud option at [zitadel.com](https://zitadel.com/).
</Note>

## Migrating from the Zitadel installer

Deployments created with the legacy `getting-started-with-zitadel.sh` script use Zitadel directly as the IdP, with
their own Caddy, Zitadel and database containers. You can:

- **Keep using Zitadel standalone.** No changes needed.
- **Move to the `configure.sh` stack and add Zitadel as a Dex connector**, following the steps above. Users keep
  logging in with Zitadel, but their openZro user records change: Dex gives each user a new ID, so users come back as
  new users and need their roles and groups assigned again. See
  [Switching from an External IdP to the Embedded Dex](/selfhosted/migration/external-to-embedded-idp).

## Troubleshooting

### "Invalid redirect URI" error

- Verify the redirect URI exactly matches what's configured
- Check for trailing slashes
- Ensure the application type is **Web** with the **Code** authentication method
