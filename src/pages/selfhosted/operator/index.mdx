# openZro Kubernetes Operator

The openZro operator reconciles openZro's domain objects (groups,
policies, peers, setup keys, network resources) from Kubernetes
manifests so GitOps + multi-tenant patterns work naturally. It's
**optional** — you can run the chart without the operator and
manage everything from the dashboard.

The operator lives in
[openzro/openzro-operator](https://github.com/openzro/openzro-operator)
and ships as its own Helm chart, `openzro/openzro-operator`, on the
same release feed as the main `openzro` chart. All versions are
prereleases, so install it with `--devel`.

To install and use it, follow
[Kubernetes integration](/manage/integrations/kubernetes): it covers
the access token Secret, the chart values, cert-manager, routing
peers and exposing Services.

## When to use the operator

Use the operator when:

- You manage your infrastructure declaratively (Argo CD, Flux,
  Terraform with the K8s provider)
- You run multiple openZro tenants and want each tenant's
  resources defined in their own namespace
- You deploy routing peers / gateways as workloads inside the
  same Kubernetes cluster as your control plane
- You want pull-request-driven changes to access policies

Skip the operator when:

- You manage a small fleet from the dashboard and prefer the GUI
- Your routing peers are all bare-metal / VM (use
  [openzro-ansible](https://github.com/openzro/openzro-ansible)'s
  `openzro_routing_peer` role instead)
- You're prototyping and don't want a second control plane to
  reason about

## How it works

The operator watches custom resources in the cluster and
translates them into management-API calls against the openZro
control plane:

```
┌────────────────┐   watch    ┌──────────────┐
│  CR (OZGroup,  │──────────▶│   operator   │
│  OZPolicy, …)  │            │  reconciler  │
└────────────────┘            └──────┬───────┘
                                     │ HTTPS + PAT
                                     ▼
                              ┌──────────────┐
                              │  management  │
                              │      API     │
                              └──────────────┘
```

Each CR has a `Status` subresource the operator updates after
each reconcile pass — `kubectl describe ozgroup my-team` shows the
`Ready` condition and, when it is `False`, the error it hit.

The operator authenticates against the management API with the
access token of a [service user](/manage/public-api), stored in a
Kubernetes Secret. Rotating it is a Secret update and a pod restart.

## Supported CRDs (today)

| CRD | What it represents |
|---|---|
| `OZGroup` | An openZro group |
| `OZPolicy` | An access control policy between groups |
| `OZSetupKey` | A reference to a setup key Secret, used to inject openZro sidecars into pods |
| `OZRoutingPeer` | A Deployment of routing peers, with the network, group and setup key it needs |
| `OZResource` | A network resource, usually created from an annotated Service |

The `openzro.io/v1alpha1` kinds (`Group`, `SetupKey`,
`NetworkResource`, `NetworkRouter`, `SidecarProfile`) back the
[Gateway API integration](/manage/integrations/kubernetes/gateway-api-beta).

Each CRD is documented with its full spec on the
[CRDs](/selfhosted/operator/crds) page.

<Note>
The Gateway API `HTTPRoute` path (public reverse proxy) depends on a
reverse-proxy API that the management server does not implement yet;
those resources apply cleanly but do not reconcile. Track via
[ADR-0008 Stage 3](https://github.com/openzro/openzro/blob/main/docs/adr/0008-kubernetes-helm-operator.md#stage-3--server-side-handlers-for-dns-zones--reverse-proxy-services).
</Note>
