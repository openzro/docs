# Splitting Your Self-Hosted Deployment

The stack generated by `configure.sh` runs every service on one machine: `dashboard`, `management`, `signal`,
`relay`, `dex` and `coturn`, each in its own container. Because the services are already separate, you can move some of
them to other machines as your deployment grows:

- **Relays** carry traffic between peers that cannot connect directly. Running relays close to your users, or several
  of them, improves latency and availability. See [Set Up External Relay Servers](/selfhosted/maintenance/scaling/set-up-external-relays)
  and [Multi-Region Relays](/selfhosted/maintenance/scaling/multi-region-relays).
- **Signal** only exchanges connection candidates between peers. Move it when you want to isolate it or run several
  instances. See [Set Up External Signal Server](/selfhosted/maintenance/scaling/set-up-external-signal).
- **Coturn** (STUN/TURN) can also run elsewhere: set `OPENZRO_TURN_DOMAIN` in `setup.env` and run Coturn with the same
  credentials on that host.
- **The management store** can move to PostgreSQL, which several management instances can share. See
  [PostgreSQL store](/selfhosted/postgres-store).

## How clients find the services

Clients learn every address from the management server when they log in and sync:

| Service | Where the address comes from |
|---|---|
| Signal | `Signal` in `management.json` (`OPENZRO_DOMAIN:OPENZRO_SIGNAL_PORT` by default) |
| Relays | `Relay.Addresses` in `management.json` (`OPENZRO_RELAY_ENDPOINT` by default) |
| STUN/TURN | `Stuns` and `TURNConfig` in `management.json` (`OPENZRO_TURN_DOMAIN` by default) |
| Traffic events | `Flow` in `management.json`, which defaults to the Signal address |

Management reads `management.json` only at startup, so restart it after a change. Re-running `configure.sh` rewrites
`management.json` from `setup.env`; put single-host changes into `setup.env` (`OPENZRO_RELAY_ENDPOINT`,
`OPENZRO_RELAY_DOMAIN`, `OPENZRO_TURN_DOMAIN`) and repeat hand edits, such as several relay addresses, after each run.

## Several management or signal instances

Management and signal can run as several instances behind a load balancer. They then need:

- a shared store: PostgreSQL or MySQL for management;
- a shared broker so instances can reach each other's peers: Redis (`OPENZRO_REDIS_URL`), NATS (`OPENZRO_NATS_URL`),
  or an embedded NATS cluster (`OPENZRO_BROKER=embedded` with `OPENZRO_CLUSTER_PEERS`);
- the same `WgPrivateKey` (or `OPENZRO_MGMT_WG_PRIVATE_KEY`) on every management instance.

This setup is documented for Kubernetes in [High availability](/selfhosted/kubernetes/high-availability).
