# Bacen Resolução 4.893 → openZro

This page maps the cybersecurity controls that Brazilian regulation requires of financial institutions to the openZro
features that implement them. Goal: a security team can speak to the auditor in concrete openZro terms — *"event Y in
our Activity log proves control X"*.

The mapping covers:

- **Resolução CMN nº 4.893** of 2021-02-26: cybersecurity policy and the contracting of data processing, storage and
  cloud services by institutions authorized by the Banco Central do Brasil. It replaced Resoluções CMN 4.658/2018 and
  4.752/2019.
- **Resolução BCB nº 85** of 2021-04-08: the equivalent rule for payment institutions. It replaced most of Circular
  nº 3.909/2018 from 2021-08-01.

Article numbers below reference Resolução CMN 4.893. Check the current consolidated text at the Banco Central, since
the resolution has been amended since 2021.

## Detailed mapping

### Art. 3º, §2º — authentication

The policy's procedures and controls must cover, at minimum, authentication. openZro provides two layers:

- **User identity.** Dashboard and interactive client logins go through openZro's bundled Dex. Dex holds local users
  and federates to the operator's identity providers (Google, Microsoft Entra ID, Okta, Keycloak, GitHub, or any
  generic OIDC provider). JWT validation enforces issuer, audience and signature, and rejects tokens with `iat` in the
  future.
- **Second factor.** openZro has built-in TOTP two-factor authentication for local accounts and, optionally, for
  federated accounts, and can require it when a device signs in. See
  [Multi-factor authentication](/manage/settings/multi-factor-authentication). Federated users can also be required to
  use MFA at their identity provider.
- **Device identity.** The peer's WireGuard public key is the device identifier. Device Admission attaches an endpoint
  compliance check (Intune, CrowdStrike, SentinelOne or Huntress), so a key whose device fails compliance does not
  reach the mesh.

**Audit artefact:** every refused device login produces a `peer.admission.deny` event. The CSV export delivers a
portable artefact with columns the auditor recognises.

### Art. 3º, §2º — access control and network segmentation

Policies, Groups and per-policy posture checks compose into per-application network segmentation. Administrative
access is split by roles in the dashboard, and every API endpoint is scoped to the account. The
[SCIM 2.0 endpoint](/manage/team/idp-sync) lets the operator's identity provider push users and group memberships, so
group-based segmentation follows the identity source of truth. Roles are assigned in openZro.

Activity events: `policy.add/update/delete`, `user.role.update`, `user.group.add/delete`, `service.user.create`.

### Art. 3º, §2º — encryption

- **In transit:** peer traffic is WireGuard. The control plane (gRPC) and the dashboard and API (HTTPS) use TLS when
  deployed behind TLS, which the operator configures.
- **At rest:** credentials for outbound integrations (MDM/EDR, SIEM endpoints, S3 / GCS exports) are stored as
  AES-256-GCM ciphertext under the management's `DataStoreEncryptionKey`.

### Art. 3º, §2º — periodic vulnerability testing and scanning

Open advisories are tracked in the project's `docs/security/advisories.md`. Every CVE that touches the dependency
tree is triaged and assigned a status: Fixed (with commit reference), Not applicable (with reasoning), or Open (with
tracking note). The project's CI does not yet run automated dependency vulnerability scanning; operators should scan
the images they deploy as part of their own vulnerability routine.

### Art. 3º, III and §2º — traceability

The Activity log captures every administrative action and every Device Admission decision. Events live in the
management's primary database; the [Activity Streamer](/manage/activity/event-streaming) fans them out to the
operator's SIEM in real time. Two layers:

- **Process-wide env-var baseline** — `OPENZRO_ACTIVITY_EXPORT_*` configures HTTP webhook / Datadog / Elastic for the
  whole instance.
- **Per-account configuration** — managed under **System → Integrations → Activity Streamer**. Credentials are
  encrypted at rest.

Both layers support custom Go-template payloads, so events can be reshaped to match the SIEM's schema without standing
up Vector or Fluent Bit in between.

### Art. 3º, IV — incident recording

Two evidence streams feed incident response:

- **Activity log** — *who did what, when*: admin actions, posture-check changes, admission denials, settings changes.
- **Flow Traffic** — *what traffic went where*: per-connection records (source and destination IP, port, protocol,
  bytes, drops, rule ID). Viewable in the dashboard under
  [Flow Traffic](/manage/activity/traffic-events-logging) and exported to S3-compatible storage (S3, R2, B2, MinIO) or
  GCS via **System → Integrations → Flow Exports**.

### Art. 23 — five-year availability

Art. 23 requires institutions to keep, among other documents, the data and records of their control mechanisms
available to the Banco Central for five years. The Activity log's primary store is whichever database the management
is configured against, and the operator owns backup retention. The recommended posture:

1. Stream Activity events to a long-term SIEM via the Activity Streamer (Datadog Logs with a retention plan, Elastic
   with an ILM policy, or an HTTP webhook into a custom archiver).
2. Use the admission CSV export periodically as a portable artefact.
3. For Flow Traffic, configure a flow export to S3-compatible storage or GCS (NDJSON+gzip by default) with a five-year
   retention policy.

### Remote access controls

Specific controls and how openZro covers them:

- **Multi-factor authentication** — openZro's built-in TOTP, the identity provider's MFA, or both.
- **Device verification** — Device Admission with MDM/EDR posture checks: the device must be in good standing in the
  corporate MDM/EDR.
- **Least-privilege access** — Policies + Groups + per-policy posture checks.
- **Session monitoring** — Flow Traffic provides per-connection monitoring; the Activity log provides per-admin-action
  monitoring.
- **Anomaly detection** — out of openZro's scope; the operator runs this in their SIEM with the streams above as inputs.

## Auditor walkthrough

Two scripts the security team runs in front of the auditor.

### "Show me how non-compliant devices are blocked"

1. **Settings → Device Admission.** Show that **Enforce admission on Login & Sync** is on and the posture-check list is
   populated.
2. **Security → Posture Checks.** Open the Endpoint Security check pointed at the corporate MDM/EDR. Show the provider
   under **System → Integrations → MDM / EDR**.
3. **Activity.** Filter by `peer.admission.deny`. Walk through a recent denial — the row carries the peer hostname, the
   failing check, and the reason verbatim from the vendor.
4. **Settings → Device Admission → Audit CSV.** The downloaded file is the artefact the auditor takes home.

### "Show me how a compromised endpoint loses access"

1. Walk through the revalidator's interval (default 60s, set with `OPENZRO_ADMISSION_REVALIDATE_INTERVAL_SECONDS`) and
   the MDM/EDR provider's cache TTL (5 minutes by default, configurable per provider) — about 6 minutes worst case.
2. Show the `peer.admission.deny` event for the device. The peer's connection to management is closed when the denial
   is recorded.
3. Show that the peer keeps producing `peer.admission.deny` on each retry until the device is fixed at the vendor.
